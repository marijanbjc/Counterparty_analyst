# Несостыковки и правки

Реестр расхождений между тем, что лежит в данных, и тем, что делает с ними код.
Сюда попадают находки, требующие правки, но не внесённые немедленно, — чтобы они
не терялись между итерациями.

Формат записи: суть, где обрывается цепочка, следствие, предлагаемая правка.
**Правки в код по этому файлу не внесены.**

Версия: 2026-09-03.

| # | Несостыковка | Где | Приоритет | Статус |
|---|---|---|---|---|
| 1 | Банкротство контрагента не доходит ни до модели, ни до пользователя | `core/factpack.py`, `core/discrepancy.py` | высокий | открыта |
| 2 | Роли анализа теряют половину разделов факторов риска | `core/roles.py` | средний | открыта |
| 3 | Бюджет контекста исчерпан до первой реплики пользователя | `config/internal_config.yaml` | высокий | открыта |
| 4 | Тип `FactPack` на фронте отстал от факт-пакета | `src/ui/src/types.ts` | низкий | открыта |
| 5 | Белого списка ИНН сессии нет ни в одном слое | агентный слой (не написан) | высокий | открыта |

## 1. Банкротство не доходит до пользователя

**Суть.** В данных статус контрагента состоит из двух частей: `report.status.status`
и `report.status.reasonName`. Первое равно `CURRENT` **у всех 100 контрагентов**
снапшота, то есть само по себе не несёт информации. Реальное содержание —
во втором поле, и оно заполнено у трёх контрагентов:

| Компания | ИНН | `reasonName` | Светофор |
|---|---|---|---|
| ООО «МАКСМАРКЕТ» | 5032257375 | признано несостоятельным (банкротом), открыто конкурсное производство | **LOW / GREEN** |
| ООО «РАДО АЛАТЫРЬ КС» | 2100006761 | решение о предстоящем исключении из ЕГРЮЛ | **LOW / GREEN**, ноль негативных факторов |
| ООО «БИЛД-ЮГ» | 2311304742 | решение об изменении места нахождения | LOW / GREEN |

**Где обрывается цепочка.**

1. Загрузчик поле читает: `scripts/load_data.py` кладёт его в колонку
   `contractors.status_reason`. До этого места всё в порядке.
2. `src/core/factpack.py` собирает блок `profile` и берёт из статуса **только**
   `contractor.status`. `status_reason` в факт-пакет не попадает — значит, модель
   его не видит и не может о нём сказать.
3. `src/core/discrepancy.py` содержит шесть правил, и ни одно не обращается
   к `status_reason`.

**Следствие.** Контрагент в процедуре банкротства выглядит в интерфейсе как
действующая компания с зелёным светофором. Это прямо противоречит основной ценности
продукта — подсвечивать расхождение между формальной оценкой и фактами.

**Предлагаемая правка — два изменения.**

*Первое, `core/factpack.py`.* Добавить `status_reason` в факт-пакет вместе
с детерминированной градацией критичности:

| Причина | `severity` |
|---|---|
| признано банкротом, открыто конкурсное производство | `critical` |
| решение о предстоящем исключении из ЕГРЮЛ | `critical` |
| изменение места нахождения | `attention` |
| уменьшение уставного капитала | `attention` |
| причины нет | `none` |

Градация согласована с кейсодателем: «часто это маркеры грядущих изменений —
переезд адреса реже, снижение УК чаще — проверить».

*Второе, `core/discrepancy.py`.* Добавить седьмое правило `green_but_status_reason`
по образцу существующих: `severity = critical` при зелёном светофоре
(`risk_level in {LOW}` и `zsk_risk_level = GREEN`) → пометка в списке расхождений.

Порог здесь не нужен и подбирать его нечего — правило срабатывает по наличию
конкретной причины, а не по числовому значению.

**Второй, независимый признак того же кейса.** У МАКСМАРКЕТ должность руководителя —
`КОНКУРСНЫЙ УПРАВЛЯЮЩИЙ` (`foundersInfo.authPerson.positionName`). Это единственное
такое значение в базе: у остальных `ГЕНЕРАЛЬНЫЙ ДИРЕКТОР` (51), `ДИРЕКТОР` (21)
или `ПРЕДСЕДАТЕЛЬ` (2). То есть банкротство видно и через должность руководителя,
и поле это в факт-пакет попадает. Отдельного правила не требует, но в описании
`get_basic_info` (`mcp_architecture.md` §9.1) на это указано явно — чтобы модель
считывала признак даже до внесения правки.

**Проверка после внесения.** На снапшоте правило обязано дать ровно два срабатывания:
МАКСМАРКЕТ и РАДО АЛАТЫРЬ КС. БИЛД-ЮГ получает `attention` и в расхождения не попадает.

## 2. Роли анализа теряют половину разделов

**Суть.** Каждый фактор риска в данных размечен полем `chapter` — к какому разделу
отчёта он относится. Всего в снапшоте встречается **десять** значений `chapter`.
Файл `src/core/roles.py` сопоставляет роль анализа со списком разделов и упоминает
**пять** из них:

```
finance  → finance
legal    → arbitr, execproc
security → reestrs, manager
general  → все
```

Не упомянуты: `okved`, `relatedComp`, `license`, `site`, `filials`.

**Где обрывается цепочка.** `core/factpack.py` вызывает `chapters_for(role)`
и фильтрует факторы по полученному списку. Разделы вне списка отсекаются
для всех ролей, кроме «Общий».

**Следствие.** Фактор `massOkved` имеет `chapter = okved` и потому не входит
ни в одну роль. Это **второй по частоте негативный фактор в базе — 25 срабатываний**,
уступает только `arbitrationDefendant` (32). Пользователь, выбравший роль
«Безопасность», не увидит признак фирмы-однодневки, хотя это ровно фактор
безопасности. Аналогично теряются `relatedComp` (61 контрагент) и `license`.

Распределение по разделам в снапшоте:

| `chapter` | Негативных | Позитивных | В какой роли сейчас |
|---|---:|---:|---|
| `arbitr` | 32 | 68 | legal |
| `reestrs` | 29 | 788 | security |
| `okved` | **25** | 75 | **нигде** |
| `execproc` | 18 | 82 | legal |
| `finance` | 7 | 136 | finance |
| `manager` | 3 | 297 | security |
| `relatedComp` | 0 | 61 | **нигде** |
| `site` | 0 | 11 | **нигде** |
| `license` | 0 | 9 | **нигде** |
| `filials` | 0 | 2 | **нигде** |

**Предлагаемая правка.** Дописать недостающие разделы в тот же словарь
`ROLE_CHAPTERS`:

```
finance  → finance
legal    → arbitr, execproc, license
security → reestrs, manager, okved, relatedComp
general  → все
```

`site` и `filials` — справочные, им место в общем профиле, а не в ролевом фильтре.

**Проверка после внесения.** Роль «Безопасность» на контрагенте с `massOkved`
обязана показать этот фактор; сейчас не показывает.

**Примечание на будущее.** Когда появятся MCP-инструменты, роль логичнее сопоставлять
с набором инструментов, а не с набором `chapter` (`mcp_architecture.md` §2.4:
фактор едет вместе с фактом, который он объясняет). Но это отдельная задача,
и до появления инструментов достаточно дописать словарь.

## 3. Бюджет контекста исчерпан до первой реплики пользователя

**Суть.** В `config/internal_config.yaml` задано `context_token_budget: 8000`.
Замер того, что уходит в модель **до** первого сообщения пользователя
(токенизатор `o200k_base`, то же семейство, что у GPT-OSS):

| Блок | Токенов |
|---|---:|
| Описания и схемы 23 инструментов | 3 276 |
| Факт-пакет `full`, максимум по базе | 3 740 |
| Якорь сессии (5 контрагентов × 180) | 900 |
| Системный промпт и правила роли | ~600 |
| **Итого** | **~8 500** |

**Следствие.** Бюджет превышен ещё до того, как пользователь что-то написал.
По правилам сборки контекста (`architecture.md` §10.1) первой режется история
диалога — значит, агент теряет её с первого же сообщения и перестаёт быть
диалоговым. Это ровно та проблема, ради которой строился якорь сессии.

**Почему значение выбрано неудачно.** Окно GPT-OSS-120B — 131 072 токена.
Ограничение 8 000 не следует ни из модели, ни из стоимости: это примерно 6 %
доступного окна.

**Предлагаемая правка.** Поднять `context_token_budget` до **24 000–32 000**.
Даже верхняя граница остаётся консервативной — четверть окна. Отдельно стоит
учесть, что после ролевой фильтрации набора инструментов (§9 `mcp_architecture.md`)
их стоимость падает с 3 276 до 1 500–1 800 токенов, но это не отменяет
необходимости поднять сам лимит.

**Проверка после внесения.** Диалог на 10 реплик по одному контрагенту не должен
приводить к обрезке истории.

## 4. Тип `FactPack` на фронте отстал от факт-пакета

**Суть.** При реализации MCP расширен `core/aggregates._arbitration_side`: поле
`pending` (только количество) заменено парой `pending_count` и `pending_amount`.
Без суммы открытых требований нельзя посчитать текущую долговую нагрузку
(`get_debt_burden`), а она — ключевой сигнал по методике кейсодателя.

**Где расходится.** `src/ui/src/types.ts` объявляет
`as_defendant?: { count?: number; amount?: number; pending?: number }`.

**Следствие.** Ошибки нет: поле необязательное, а `Dossier` в `Workspace.tsx`
его не отображает — сейчас показывается только `arbitration.total_count`.
Но тип описывает несуществующее поле и не описывает два новых.

**Предлагаемая правка.** В `types.ts` заменить `pending?: number` на
`pending_count?: number; pending_amount?: number`. Заодно стоит показать открытые
дела в карточке: это текущий риск, в отличие от завершённых, и сейчас
пользователь их не видит.

**Проверка после внесения.** Карточка ЛЕ МОНЛИД (ИНН 5029069967) должна
показывать 17 открытых дел в роли ответчика на 69 623 415 ₽.

## 5. Белого списка ИНН сессии нет ни в одном слое

В отличие от записей 1–4 это не дефект существующего кода, а **недостающий
компонент**: он относится к агентному слою, которого пока нет. Запись заведена,
чтобы его не забыли при сборке агента.

**Суть.** Белый список — множество ИНН, законно появившихся в текущей сессии.
Вызов любого инструмента с ИНН вне множества должен отклоняться, не доходя до базы.
Источники пополнения — три, и все внешние по отношению к «памяти» модели:

| Откуда | Что добавляется |
|---|---|
| сообщение пользователя | результат `inn_module.extract`, прошедший контрольный разряд |
| ответ `get_affiliations` | `items[].inn` связанных компаний |
| ответ `find_similar_contractors` | `items[].inn` найденных |

**От чего защищает.** От сценария, который хуже галлюцинации: **уверенный ответ
про другую компанию**. Модель может подставить в инструмент ИНН, который
пользователь не называл — необязательно выдуманный с нуля, достаточно переставить
две цифры в увиденном выше по диалогу. Если получившийся ИНН случайно есть в базе,
инструмент вернёт подлинные данные подлинной компании, модель уверенно их
перескажет, и пользователь примет решение по чужому контрагенту. Ошибки в системе
при этом не возникнет: все данные настоящие, просто не те.

**Почему остальные слои не ловят** (`architecture.md` §9.1):

| Слой | Что делает | Почему не хватает |
|---|---|---|
| 1. Формат и контрольный разряд | ловит опечатки и обрывки | правдоподобный ИНН проверку проходит |
| 2. Закрытый мир | ИНН вне базы → отказ | ИНН **внутри** базы вернёт реальные данные |
| 3. `resolve_contractor` | позволял брать ИНН из ответа инструмента | **удалён** решением по проекту (`mcp_architecture.md` §4.1) |
| 4. Белый список | ИНН вне сессии → отказ | **не реализован** |

Третий слой снят сознательно, поэтому нагрузка легла на четвёртый. Пока его нет,
между «модель ошиблась цифрой» и «пользователь читает досье не той компании»
не стоит ничего.

**Почему не в MCP.** Инструменты MCP по природе stateless: контекста сессии
у вызова нет. Передавать `session_id` параметром инструмента нельзя по двум
причинам: его подставляет модель — то есть защитой управляет тот, от кого
защищаемся; и это лишнее поле в схеме каждого из 24 инструментов, то есть плата
токенами на каждом шаге.

**Место — диспетчер агентного слоя**, код между `tool_call` от модели и вызовом
MCP: он ведёт сессию и знает `session_id`.

**Что предстоит сделать.**

*Хранение.* Таблица `session_inns(session_id, inn, source, created_at)`.
Вариант без новой таблицы — пересобирать множество из `messages`: там есть
и реплики пользователя, и `meta` с ответами инструментов.

*Пополнение* на двух событиях:
* пришло сообщение пользователя → `inn_module.extract(text)` → добавить;
* вернулся ответ инструмента с `found: true` → добавить `result["inn"]`,
  а для `get_affiliations`, `find_similar_contractors` и `compare_contractors` —
  ещё и ИНН из `items` / `matrix`.

*Проверка* перед диспетчеризацией: если у вызова есть аргумент `inn` или `inns`
и значение вне множества, вернуть модели отказ вместо вызова инструмента:

```json
{"found": false, "reason": "inn_not_in_session",
 "hint": "Этот ИНН в диалоге не назывался. Уточните его у пользователя."}
```

Отказ **не перечисляет** разрешённые ИНН — по той же причине, по которой их
не перечисляет `not_in_database`: иначе на каждой ошибке модели выдаётся список,
из которого она возьмёт «любой подходящий».

**Половина контракта уже написана.** `core/validation.py` принимает
`context["allowed_inns"]` и проверяет, что все ИНН в тексте ответа принадлежат
этому множеству. Диспетчеру нужно собрать список один раз, а использовать дважды:
на входе — гейт вызовов инструментов, на выходе — валидатор ответа. Обе стороны
замыкаются на одно множество, и это делает защиту цельной, а не двумя
разрозненными проверками.

**Проверка после внесения.** Вызов `get_contractor_full` с ИНН, который есть
в базе, но не назывался в диалоге, должен вернуть `reason: "inn_not_in_session"`,
а не данные контрагента. Переход по связанной компании из `get_affiliations`
при этом обязан продолжать работать.
