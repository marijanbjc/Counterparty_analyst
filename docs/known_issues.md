# Несостыковки и правки

Реестр расхождений между тем, что лежит в данных, и тем, что делает с ними код.
Сюда попадают находки, требующие правки, но не внесённые немедленно, — чтобы они
не терялись между итерациями.

Формат записи: суть, где обрывается цепочка, следствие, предлагаемая правка.
**Правки в код по этому файлу не внесены.**

Версия: 2026-09-03.

| # | Несостыковка | Где | Приоритет | Статус |
|---|---|---|---|---|
| 1 | Банкротство контрагента не доходит ни до модели, ни до пользователя | `core/factpack.py`, `core/discrepancy.py` | высокий | открыта |
| 2 | Роли анализа теряют половину разделов факторов риска | `core/roles.py` | средний | открыта |

## 1. Банкротство не доходит до пользователя

**Суть.** В данных статус контрагента состоит из двух частей: `report.status.status`
и `report.status.reasonName`. Первое равно `CURRENT` **у всех 100 контрагентов**
снапшота, то есть само по себе не несёт информации. Реальное содержание —
во втором поле, и оно заполнено у трёх контрагентов:

| Компания | ИНН | `reasonName` | Светофор |
|---|---|---|---|
| ООО «МАКСМАРКЕТ» | 5032257375 | признано несостоятельным (банкротом), открыто конкурсное производство | **LOW / GREEN** |
| ООО «РАДО АЛАТЫРЬ КС» | 2100006761 | решение о предстоящем исключении из ЕГРЮЛ | **LOW / GREEN**, ноль негативных факторов |
| ООО «БИЛД-ЮГ» | 2311304742 | решение об изменении места нахождения | LOW / GREEN |

**Где обрывается цепочка.**

1. Загрузчик поле читает: `scripts/load_data.py` кладёт его в колонку
   `contractors.status_reason`. До этого места всё в порядке.
2. `src/core/factpack.py` собирает блок `profile` и берёт из статуса **только**
   `contractor.status`. `status_reason` в факт-пакет не попадает — значит, модель
   его не видит и не может о нём сказать.
3. `src/core/discrepancy.py` содержит шесть правил, и ни одно не обращается
   к `status_reason`.

**Следствие.** Контрагент в процедуре банкротства выглядит в интерфейсе как
действующая компания с зелёным светофором. Это прямо противоречит основной ценности
продукта — подсвечивать расхождение между формальной оценкой и фактами.

**Предлагаемая правка — два изменения.**

*Первое, `core/factpack.py`.* Добавить `status_reason` в факт-пакет вместе
с детерминированной градацией критичности:

| Причина | `severity` |
|---|---|
| признано банкротом, открыто конкурсное производство | `critical` |
| решение о предстоящем исключении из ЕГРЮЛ | `critical` |
| изменение места нахождения | `attention` |
| уменьшение уставного капитала | `attention` |
| причины нет | `none` |

Градация согласована с кейсодателем: «часто это маркеры грядущих изменений —
переезд адреса реже, снижение УК чаще — проверить».

*Второе, `core/discrepancy.py`.* Добавить седьмое правило `green_but_status_reason`
по образцу существующих: `severity = critical` при зелёном светофоре
(`risk_level in {LOW}` и `zsk_risk_level = GREEN`) → пометка в списке расхождений.

Порог здесь не нужен и подбирать его нечего — правило срабатывает по наличию
конкретной причины, а не по числовому значению.

**Проверка после внесения.** На снапшоте правило обязано дать ровно два срабатывания:
МАКСМАРКЕТ и РАДО АЛАТЫРЬ КС. БИЛД-ЮГ получает `attention` и в расхождения не попадает.

## 2. Роли анализа теряют половину разделов

**Суть.** Каждый фактор риска в данных размечен полем `chapter` — к какому разделу
отчёта он относится. Всего в снапшоте встречается **десять** значений `chapter`.
Файл `src/core/roles.py` сопоставляет роль анализа со списком разделов и упоминает
**пять** из них:

```
finance  → finance
legal    → arbitr, execproc
security → reestrs, manager
general  → все
```

Не упомянуты: `okved`, `relatedComp`, `license`, `site`, `filials`.

**Где обрывается цепочка.** `core/factpack.py` вызывает `chapters_for(role)`
и фильтрует факторы по полученному списку. Разделы вне списка отсекаются
для всех ролей, кроме «Общий».

**Следствие.** Фактор `massOkved` имеет `chapter = okved` и потому не входит
ни в одну роль. Это **второй по частоте негативный фактор в базе — 25 срабатываний**,
уступает только `arbitrationDefendant` (32). Пользователь, выбравший роль
«Безопасность», не увидит признак фирмы-однодневки, хотя это ровно фактор
безопасности. Аналогично теряются `relatedComp` (61 контрагент) и `license`.

Распределение по разделам в снапшоте:

| `chapter` | Негативных | Позитивных | В какой роли сейчас |
|---|---:|---:|---|
| `arbitr` | 32 | 68 | legal |
| `reestrs` | 29 | 788 | security |
| `okved` | **25** | 75 | **нигде** |
| `execproc` | 18 | 82 | legal |
| `finance` | 7 | 136 | finance |
| `manager` | 3 | 297 | security |
| `relatedComp` | 0 | 61 | **нигде** |
| `site` | 0 | 11 | **нигде** |
| `license` | 0 | 9 | **нигде** |
| `filials` | 0 | 2 | **нигде** |

**Предлагаемая правка.** Дописать недостающие разделы в тот же словарь
`ROLE_CHAPTERS`:

```
finance  → finance
legal    → arbitr, execproc, license
security → reestrs, manager, okved, relatedComp
general  → все
```

`site` и `filials` — справочные, им место в общем профиле, а не в ролевом фильтре.

**Проверка после внесения.** Роль «Безопасность» на контрагенте с `massOkved`
обязана показать этот фактор; сейчас не показывает.

**Примечание на будущее.** Когда появятся MCP-инструменты, роль логичнее сопоставлять
с набором инструментов, а не с набором `chapter` (`mcp_architecture.md` §2.4:
фактор едет вместе с фактом, который он объясняет). Но это отдельная задача,
и до появления инструментов достаточно дописать словарь.
