# Архитектура: ИИ-агент проверки контрагентов

Документ фиксирует принятые решения и служит планом работ.
Разбор исходных данных — в `data_profile.md`.
Версия: 2026-09-03. Статус: согласовано, к реализации.

---

## 1. Задача и критерии успеха

Веб-чат, в котором пользователь проверяет контрагента (или нескольких сразу) по ИНН
и получает структурированный анализ рисков с вердиктом, а затем задаёт уточняющие вопросы 
(или сразу задает вопросы по базе контрагентов).

Оценка экспертная. Решение успешно, если агент:
1. **не выдумывает информацию**;
2. **использует только входные данные**;
3. отвечает на большинство вопросов при тестировании заказчиком.

Всё остальное в этом документе подчинено пунктам 1 и 2.

**Главный архитектурный принцип, который из них следует:**

> Все факты, числа и агрегаты считает **детерминированный Python-код**.
> LLM получает готовый *факт-пакет* и только **формулирует текст и ведёт диалог**.
> LLM не имеет доступа к сырым данным и не выполняет арифметику.

## 2. Ключевые решения

| # | Решение | Обоснование |
|---|---|---|
| 1 | Вердикт строим на `baseInfo.riskLevel`. ЗСК показываем как есть, расхождения **помечаем** | см. §3.2 — светофора два, и они расходятся |
| 2 | Работаем только со 100 компаниями из снапшота. Веб-поиск — задел, не делаем | метрика «только входные данные» |
| 3 | Снапшот один, версионности отчётов нет | упрощение; `_id.date` кладём как атрибут |
| 4 | **Источник истины в рантайме — Postgres.** JSON — только сид при старте, CSV не используется | §6; в CSV массивы развёрнуты в 2654 колонки |
| 5 | Postgres: гибрид — нормализация «горячих» сущностей + JSONB для остального | §5 |
| 6 | Свои финансовые коэффициенты **не считаем**. Нет `coefficient` — «нет данных» | решение по проекту |
| 7 | LLM — внешняя по API (GPT-OSS-120B через Groq). Обязателен degraded-режим | §14 |
| 8 | MCP-сервер (FastMCP) — базовые инструменты сейчас, продвинутые заложены | §9 |
| 9 | Валидатор ответов — детерминированный. LLM-валидатор заложен, но не делается | §11 |
| 10 | Фронт: **Vite + React + TS** + `@alfalab/core-components`. Next.js не берём | SSR не нужен, бэкенд — FastAPI |
| 11 | Отчёт пользователю: JSON + Markdown в чат сразу; PDF — если останется время | кириллица в PDF требует подключения шрифта |
| 12 | RAG/векторный поиск не используем | база невелика, прямой доступ к БД точнее |
| 13 | Память сессии: детерминированный якорь + MCP-ручки доскока — агент не «тупеет» после обрезки окна | §10.1 |
| 14 | Авторизация базовая: окно логина, один пользователь из конфига | §17 |

## 3. Ограничения, вытекающие из данных

Измерения, распределения и разбор снапшота — в `data_profile.md`.
Здесь только те свойства данных, которые определяют контракты компонентов.

| Свойство данных | Что из него следует в архитектуре |
|---|---|
| Уровней риска два (`riskLevel` и `zskRiskLevel`), и они расходятся | вердикт строится на `riskLevel`, ЗСК показывается как есть, расхождение помечается детектором (§3.1) |
| В базе не только организации, но и предприниматели | валидация ИНН принимает 10 и 12 знаков; в факт-пакете есть `entity_kind`, а КПП, учредители и уставный капитал для ИП помечаются как неприменимые, а не отсутствующие |
| Конкретных судебных дел в источнике нет, только агрегаты | инструмента «список дел» не существует; `get_arbitration_stats` объявляет `granularity: aggregates_only` |
| Часть полей заполнена не у всех контрагентов | инструменты возвращают явный маркер отсутствия; ноль вместо отсутствия запрещён |
| Отдельные отчёты на два порядка больше остальных | тяжёлые массивы всегда агрегируются кодом, в модель уходит факт-пакет ограниченного размера (§7) |
| Числа приходят как `$numberLong`, суммы строками, коды факторов содержат кириллические омоглифы | нормализация вынесена в `core/normalize.py` и применяется на загрузке (§6) |
| Регион лежит фиксированным элементом адреса | вырезается кодом в колонку `region`; сопоставление запроса с регионом — выбор модели из закрытого списка (§9.2) |
| Стороны арбитража не суммируются в общий счётчик | общее число берётся из `commonCount`, суммирование сторон запрещено |

### 3.1. Детектор расхождений

Светофор бывает зелёным при объективно тревожных фактах — это и есть основная
ценность продукта поверх исходного отчёта. Правила детерминированные,
в `core/discrepancy.py`:

| Код | Условие | Смысл пометки |
|---|---|---|
| `green_but_execproc` | светофор LOW/GREEN и сработал хотя бы один порог из трёх | зелёный светофор при действующих взысканиях |
| `green_but_negative` | светофор LOW/GREEN и негативных факторов не меньше порога | формально низкий риск при множестве негативных факторов |
| `many_closed_execproc` | всего производств не меньше порога | историческая долговая нагрузка, отдельно от текущей |
| `traffic_lights_disagree` | `riskLevel=HIGH` при `zskRiskLevel=GREEN` и обратный случай | оценки риска противоречат друг другу |
| `unknown_risk` | `riskLevel = UNKNOWN` | банк не присвоил уровень риска |
| `no_financials` | нет финансовой отчётности | нечем оценить финансовое состояние |

Порог `green_but_execproc` относительный — доля активных взысканий от выручки,
с подпорками для случая отсутствия отчётности и для абсолютной суммы.
Абсолютный порог сам по себе непригоден: одна и та же сумма для микропредприятия
критична, а для крупной компании находится в пределах погрешности.

Все пороги — параметры `config`, подбор и результаты замеров в `data_profile.md`.

## 6. Загрузчик (`scripts/load_data.py`)

**JSON — только сид. После загрузки к файлам не обращается никто:**
ни MCP-инструменты, ни агент, ни API. Единственный источник данных
в рантайме — Postgres. CSV не используется вообще.

Запускается командой `python app.py load-data` (в контейнере — на старте), идемпотентен.
Создаёт таблицы через `Base.metadata.create_all`, миграций нет (§18).
Проверяет отпечаток файла (хэш + количество записей): если в БД уже
лежит тот же снапшот — загрузка пропускается, старт не тормозит.

1. Читает JSON, разворачивает Extended JSON (`$date`, `$numberLong`).
2. Приводит типы: строковые `amount` и коэффициенты → numeric.
3. **Нормализует коды факторов** (кириллические омоглифы → латиница).
4. `TRUNCATE` + `INSERT` в нормализованные таблицы, полный `report` — в `contractors.raw`.
5. Считает и кладёт производные: `okved_count`, агрегаты по ИП — денормализованно
   в `contractors`, чтобы не джойнить на каждый запрос.
6. Пишет отпечаток снапшота в служебную таблицу `snapshot_meta`.
7. Логирует статистику загрузки и список пропущенных/битых полей.

## 7. Факт-пакет — контракт между кодом и LLM

Единственное, что видит модель. Размер ограничен и предсказуем независимо от того,
насколько велик исходный отчёт: тяжёлые массивы агрегируются кодом.
Замеренные размеры обоих режимов — в `data_profile.md`.
Каждое значение сопровождается путём к исходному полю — для ссылок в ответе
(требование «использует только входные данные») и для работы валидатора.

  "verdict_basis": {                        // §3.2

## 8. Роли (предзаданные виды анализа)

Роли ложатся на поле `chapter` из `reputationalRisks` — данные уже размечены:

| Роль в UI | chapters | Что в фокусе |
|---|---|---|
| Финансовый | `finance` | выручка, прибыль, тренды, активы/пассивы |
| Юридический | `arbitr`, `execproc` | арбитраж (агрегаты!), исполнительные производства, лицензии |
| Безопасность | `reestrs`, `manager` | реестры ФНС, массовость, номинальный руководитель, связанные компании |
| Общий | все | сводка по всем разделам |

Роль влияет на: системный промпт, порядок блоков в факт-пакете и в отчёте.
Хранится в `sessions.role_preset`, переключается в любой момент.

## 9. MCP-сервер (FastMCP)

Инструменты — тонкие обёртки над SQL. Описание каждого инструмента —
часть промпта, поэтому в описаниях **явно указываются границы данных**.

### Базовые (делаем)

| Инструмент | Сигнатура | Примечание |
|---|---|---|
| `get_contractor_profile` | `(inn) -> compact fact-pack` | сокращённый пакет, для сравнения нескольких |
| `get_contractor_full` | `(inn) -> full fact-pack` | карточка одной компании |
| `get_basic_info` | `(inn)` | наименование, регистрация, ген. дир., **телефон (29/100)**, адрес (75/100), ОКВЭД |
| `get_financials` | `(inn, year_from?, year_to?)` | выручка, прибыль, убыток; часть показателей в отчётности отсутствует |
| `get_liabilities` | `(inn, year?)` | заёмные средства, задолженности, обязательства; данных < 50 % |
| `get_arbitration_stats` | `(inn, year_from?, year_to?)` | **только агрегаты, конкретных дел в источнике нет** |
| `get_execution_proceedings` | `(inn, active_only=true, limit=5)` | всегда агрегат + топ-N, никогда полный список |
| `get_risk_factors` | `(inn, chapter?)` | негативные/позитивные факторы, фильтр по роли |
| `get_related_companies` | `(inn)` | список, без обхода графа |
| `resolve_contractor` | `(query)` | поиск по названию **или** ИНН → кандидаты с точными ИНН; главная защита от галлюцинаций (§9.1) |
| `search_contractors` | `(filters, limit, cursor)` | по светофору, региону, ОКВЭД, наличию рисков; ответ ограничен по объёму, см. §9.2 |
| `compare_contractors` | `(inns[])` | compact-пакеты + сводная таблица |

Память сессии — отдельная группа, см. §10.1:

| Инструмент | Сигнатура | Примечание |
|---|---|---|
| `save_analysis` | `(session_id, inn, analysis_type, verdict, summary, report, analysis)` | вызывается кодом в узле `persist`, не моделью |
| `get_analysis` | `(inn, analysis_type?)` | полный сохранённый анализ — «вспомнить» после обрезки окна |
| `get_analysis_section` | `(inn, section)` | один раздел отчёта, дешевле полного |
| `list_session_analyses` | `(session_id)` | что уже разбирали в этой сессии: **ИНН + название + вердикт**, чтобы после обрезки окна модель могла взять ИНН отсюда, а не вспоминать |

Все инструменты на неизвестный ИНН возвращают `{"found": false}` — роутер отдаёт
пользователю «по этой компании у нас нет информации».

### 9.1. Защита инструментов от галлюцинаций модели

Модель может подставить в инструмент выдуманный ИНН. Защита выстроена в четыре слоя,
и главный из них — **не давать модели набирать цифры по памяти**.

**Слой 1. Формат и контрольная сумма** (`core/inn.py`). ИНН принимается только как
10 цифр (организация) или 12 (ИП), с проверкой контрольного разряда по методике ФНС.
Ловит опечатки и обрывки, но не ловит «правдоподобно выдуманный» ИНН.

**Слой 2. Закрытый мир.** База фиксирована: ИНН вне её — всегда ошибка, а не пустой ответ.
Инструмент возвращает структурированный отказ с подсказкой, а не тишину:

```json
{"found": false, "reason": "not_in_database", "inn": "5029069960",
 "hint": "Контрагента с таким ИНН в базе нет. Уточните ИНН у пользователя или найдите компанию по названию через resolve_contractor."}
```

Отказ **не перечисляет** известные ИНН — ни из базы, ни из сессии. Ошибка говорит «нет»,
а поиск живёт в `resolve_contractor`; смешивать их значит вываливать модели содержимое
базы на каждой опечатке и провоцировать её брать «любой подходящий» ИНН из списка.

**Слой 3. Поиск вместо набора цифр — `resolve_contractor(query)`.** Принимает
название или ИНН, возвращает кандидатов с точными ИНН. Модель дальше оперирует
ИНН **из ответа инструмента**, а не из головы. Это снимает саму причину проблемы,
а не последствия.

**Слой 4. Белый список ИНН сессии.** MCP-слой ведёт множество ИНН, которые в этой
сессии легитимно появились: извлечённые из сообщений пользователя, возвращённые
`resolve_contractor` / `search_contractors`, перечисленные в якоре сессии,
а также ИНН связанных компаний из ответов инструментов. Вызов `get_*` с ИНН
вне множества отклоняется с подсказкой. Список пополняется автоматически,
поэтому легальные сценарии (переход к связанной компании) не ломаются.

### 9.2. Ограничение объёма ответов и география

**Ответ поиска — агрегат первым, строки вторым.** Список никогда не отдаётся целиком:

```json
{"total": 6,
 "breakdown": {"risk_level": {"LOW": 5, "MEDIUM": 1}, "zsk": {"GREEN": 6}},
 "returned": 6, "limit": 20, "cursor": null,
 "items": [{"inn": "5032257375", "name": "ООО \"МАКСМАРКЕТ\"",
            "risk_level": "LOW", "zsk_risk_level": "GREEN", "region": "Московская область"}]}
```

Правила:
* лимит 20 строк по умолчанию, 50 потолок, дальше курсор;
* если совпадений больше лимита — возвращаются `total` и `breakdown`, **а не список**:
  на вопрос «сколько контрагентов в Подмосковье» ответ это число, а не перечисление;
* строка минимальна (~25 токенов): ИНН, название, два светофора, регион;
* ответы инструментов вырезаются из истории при обрезке окна наравне
  со старыми факт-пакетами (§10.1).

**Регион — закрытый список, а не разбор текста.** В исходных данных адрес это
свободная строка, но формат жёсткий: `индекс, РЕГИОН, район, город, улица`.
Регион вырезается **кодом при загрузке** в колонку `contractors.region`.
Загрузка обязана быть детерминированной, поэтому LLM здесь не участвует.

Сопоставление запроса пользователя с регионом делает **модель, выбирая из закрытого
списка** значений, переданного в схеме инструмента как перечисление
(строится из БД на старте MCP-сервера). «Подмосковье» превращается
в «Московская область» без словаря синонимов, а несуществующий регион запросить
невозможно. Это тот же принцип, что и `resolve_contractor` в §9.1: модель
не воспроизводит значение по памяти, а выбирает из фактического множества.

Приблизительное сравнение (`ILIKE %...%`) запрещено: «Марс» попадает
в «СаМАРСкую область». Сравнение только точное.

Контрагенты без адреса в географическую выборку не попадают — это техническое
следствие, а не факт для пользователя (§9.3).

### 9.3. Что не раскрывается пользователю

Агент отвечает **по той базе, которую знает**, и не комментирует её полноту.
Наружу не выходят: доля заполненности полей, число контрагентов без адреса
или без отчётности, размер базы, любые формулировки вида «известно только N из M».
Ни в ответе модели, ни в поле ответа инструмента.

Граница проходит по объекту высказывания:

| Можно | Нельзя |
|---|---|
| «В отчёте не указан сайт компании» — про **запрошенного контрагента** | «У N компаний нет сайта» — статистика базы |
| «Финансовая отчётность отсутствует» — про **эту** компанию | «Отчётность есть у N из M» |
| «В Московской области — N контрагентов» | «N из M с известным адресом, у остальных адреса нет» |

Отсутствие данных по конкретному контрагенту сообщать **обязательно** —
без этого агент начнёт домысливать, а это прямое нарушение главной метрики (§1).

### Продвинутые (заложить, не делать)

Интерфейсы описать, реализацию оставить заглушками:
* `run_subagent_analysis(inn, focus)` — суб-агент под узкий разбор;
* `build_chart(data, chart_type)` — данные для графиков на фронте;
* `validate_conclusions(answer, fact_pack)` — LLM-валидатор (§11).

## 10. Агент (LangGraph)

Stateless: состояние живёт в Postgres, в модель каждый раз собирается контекст заново (§10.1).

```
        ┌──────────┐
        │  router  │  вопрос про контрагента или общий?
        └────┬─────┘
     ┌───────┴────────┐
     ▼                ▼
┌─────────┐      ┌──────────┐
│extract_ │      │ general_ │  свободный вопрос → ответ строго
│  inn    │      │  answer  │  в рамках доступных данных
└────┬────┘      └────┬─────┘
     │ regex + контрольная сумма (10/12 знаков)
     │ не вышло → Structured Output → не вышло → переспросить
     ▼
┌──────────────┐
│ fetch_facts  │  MCP: профиль(и) + разделы под роль + детектор расхождений
└──────┬───────┘
       │  не найдено → «нет информации по этой компании»
       ▼
┌──────────────┐
│  generate    │  LLM: факт-пакет + промпт роли + история → Structured Output
└──────┬───────┘
       ▼
┌──────────────┐
│  validate    │  детерминированная проверка (§11)
└──────┬───────┘
       │  провал → 1 повтор с указанием ошибки → иначе degraded-ответ
       ▼
┌──────────────┐
│ persist      │  messages + analyses + якорь сессии (§10.1)
└──────────────┘
```

### 10.1. Память сессии: агент не должен «тупеть» после обрезки

**Проблема.** Окно диалога ограничено. Если агент выдал развёрнутый отчёт,
а диалог продолжился — отчёт уедет за границу окна, и на вопрос
«а какая у него была выручка?» модель либо ответит «не знаю», либо, что хуже,
придумает. Обрезка не должна стирать результаты работы.

**Решение — два уровня. Первый работает всегда, второй по требованию модели.**

#### Уровень 1. Якорь сессии — всегда в промпте, не зависит от модели

При каждом вызове в системный промпт подставляется компактная сводка того,
что уже разобрано в этой сессии. Собирается кодом из таблицы `analyses`,
никакого решения модели не требует — а значит не может быть «забыто».

```
[Разобрано в этой сессии]
1. ООО "ЛЕ МОНЛИД" (ИНН 5029069967) — вердикт: Работать с осторожностью.
   Риск не определён / ЗСК зелёный. Данные на 2026-07-30.
   Финансовая отчётность отсутствует.
   Исп. производства: активных 45 на 1,6 млн ₽ (всего 1744 на 254,5 млн ₽).
   Арбитраж: ответчик 439, истец 1049. Негативных факторов: 4.
   ! Историческая долговая нагрузка: 1744 производств, из них активны 45
   ! Банк не смог присвоить уровень риска
   Полный отчёт: get_analysis("5029069967").
2. ООО "МАКСМАРКЕТ" (ИНН 5032257375) — вердикт: Работать.
   Риск низкий / ЗСК зелёный. Данные на 2026-07-31.
   Выручка — 2023: 116 257,9 млн ₽.
   Исп. производства: активных 54 на 4,0 млн ₽ (всего 507 на 483,7 млн ₽).
   Арбитраж: ответчик 258, истец 20. Негативных факторов: 6.
   ! Формально низкий риск при 6 негативных факторах
   Полный отчёт: get_analysis("5032257375").
```

Состав блока по каждому контрагенту фиксирован: **ИНН и название** (чтобы модель
не набирала цифры по памяти, §9.1), **вердикт**, **оба светофора**, **дата
актуальности**, **выручка по годам**, **исполнительные производства — активные и
всего**, **счётчики арбитража**, **число негативных факторов**, **до двух пометок
детектора** и **имя инструмента для полного отчёта**. Тексты факторов, баланс,
разбор и сам отчёт в якорь не попадают — они лежат в `analyses` и тянутся по требованию.

Число контрагентов в якоре ограничено параметром `context_anchor_max_contractors`,
поэтому его размер не растёт с длиной диалога. Замеренная стоимость — в `data_profile.md`;
она заведомо ниже, чем у одного полного отчёта в истории.

**Якорь всегда содержит ИНН.** Это и есть ответ на вопрос «откуда модель возьмёт ИНН
для `get_analysis`, если диалог обрезан»: ИНН не теряется никогда, потому что якорь
не режется. `list_session_analyses` — резервный путь на случай, если модель
предпочтёт спросить явно. Якорь строится в `core/context.py`.

Ключевое: **пересказ якоря — не пересказ модели, а детерминированный текст из БД.**
Числа в нём те же, что проверяет валидатор (§11), поэтому он не может «поплыть».

#### Уровень 2. MCP-ручки — доскок до полного отчёта

Если якоря не хватает (спросили про конкретную цифру из отчёта), модель
вызывает инструмент и получает сохранённый анализ целиком — **не пересчитывая его заново**:

| Инструмент | Что делает |
|---|---|
| `save_analysis(session_id, inn, analysis_type, verdict, summary, report, analysis)` | пишет `AgentReport` в `analyses` + обновляет якорь сессии. Вызывается автоматически в узле `persist`, модели дёргать не надо |
| `get_analysis(inn, analysis_type=None)` | полный сохранённый анализ: `verdict`, `summary`, `report`, `analysis` |
| `get_analysis_section(inn, section)` | один раздел отчёта (`financials`, `arbitration`, `execution_proceedings`, `risk_factors`) — дешевле, чем тянуть всё |
| `list_session_analyses(session_id)` | что уже разбирали в этой сессии: ИНН, название, вердикт, дата |

Кэш общий по `(inn, analysis_type)`, поэтому в **новой** сессии повторный
запрос по той же компании тоже поднимет готовый анализ, а не пересчитает его.

#### Сборка контекста (`core/context.py`)

Окно считается по токенам, а не по числу сообщений: фиксированное число
последних сообщений ломается, когда среди них оказывается развёрнутый отчёт. Порядок сборки и приоритет
при нехватке бюджета:

| # | Блок | Режется? |
|---|---|---|
| 1 | системный промпт + правила роли | никогда |
| 2 | факт-пакет текущего контрагента | никогда |
| 3 | якорь сессии (§ выше) | никогда |
| 4 | последние сообщения диалога | режется первым, с самых старых |
| 5 | предыдущие факт-пакеты и ответы инструментов в истории | вырезаются полностью, заменяются строкой «см. якорь» |

То есть обрезается только «болтовня», а результаты анализа остаются в контексте
в сжатом виде постоянно. Бюджет окна — параметр конфига.

Структура ответа модели:

```python
class AgentBasicAnswerToClient:
    answer: str            # реплика в чат

class AgentReport:
    verdict: str           # Работать | Работать с осторожностью | Не рекомендуется
    summary: str           # «Контрагент: LOW / ЗСК зелёный. Ключевые риски: 1. 2. 3.»
    report: dict           # структурированный отчёт (= основа выгрузки JSON/PDF)
    analysis: str          # подробный разбор с выводами и рекомендациями

class AgentFinalAnswerToClient(AgentBasicAnswerToClient, AgentReport):
    pass
```

Особенности GPT-OSS-120B: модель reasoning-типа — отдельное поле рассуждений
надо отсекать при парсинге; Structured Output через `json_schema` поддержан,
но нужен fallback на повторный запрос при невалидном JSON.

### Правила промпта (жёсткие)

1. Использовать **только** факт-пакет. Нет в пакете — «в отчёте нет этих данных».
2. Не считать самому: все производные значения уже посчитаны.
3. При упоминании числа — ссылаться на источник (поле/раздел отчёта).
4. Вердикт — по `risk_level`. `zsk_risk_level` упоминать отдельно, как есть.
5. При наличии `discrepancies` — обязательно проговорить их в ответе.
6. Про арбитраж говорить только агрегатами; **не описывать отдельные дела**.
7. Указывать дату актуальности (`as_of`).
8. Не раскрывать полноту базы: никаких «известно N из M», долей заполненности
   и размера базы. Отсутствие данных сообщается только про запрошенного
   контрагента (§9.3).

## 11. Валидатор ответов

**Делаем сейчас — детерминированный, дешёвый (миллисекунды):**

1. Извлечь из ответа модели все числа и ИНН регулярками.
2. Сверить с множеством значений из факт-пакета (с нормализацией: «254,5 млн» ↔ `254507229`, разряды, округления).
3. Найденное вне пакета → пометка `hallucinated_number`.
4. Проверить, что вердикт согласован с `risk_level`.
5. Проверить, что при непустых `discrepancies` они упомянуты в ответе.
6. При провале — один повторный запрос к модели с указанием конкретной ошибки;
   при повторном провале отдать детерминированный отчёт (§14).

Это ловит подавляющую часть галлюцинаций и напрямую закрывает главный критерий оценки.

**Заложено, не делаем:** `validate_conclusions` — LLM-проверка семантики
вторым проходом. Интерфейс инструмента объявлен, реализация — заглушка,
включается флагом в конфиге.

## 12. Backend (FastAPI)

| Метод | Ручка | Назначение |
|---|---|---|
| `POST` | `/api/auth/login` | вход по логину и паролю из конфига → `user_id` и подписанный токен |
| `GET` | `/api/me` | профиль текущего пользователя и счётчики использования |
| `GET` | `/api/sessions` | список сессий текущего пользователя (берётся из токена) |
| `POST` | `/api/sessions` | создать сессию с выбранной ролью |
| `PATCH` | `/api/sessions/{id}` | сменить роль анализа у сессии |
| `DELETE` | `/api/sessions/{id}` | удалить сессию; сообщения и связи с анализами уходят каскадом, сами анализы остаются в кэше |
| `GET` | `/api/sessions/{id}/messages` | история сессии, страницами: `limit`, `before_id` |
| `POST` | `/api/sessions/{id}/messages` | добавить сообщение вручную |
| `POST` | `/api/chat` | основная: разбирает ИНН, собирает факт-пакет, сохраняет анализ, возвращает ответ вместе с сохранёнными сообщениями и сессией |
| `GET` | `/api/sessions/{id}/analyses` | что разобрано в сессии — основа якоря (§10.1) |
| `GET` | `/api/sessions/{id}/report` | последний отчёт сессии |
| `PUT` | `/api/sessions/{id}/report` | обновить summary и разбор |
| `GET` | `/api/sessions/{id}/report/export?format=json\|md` | выгрузка; имя файла `report-<ИНН>-<дата отчёта>`. Интерфейс скачивает JSON — он несёт весь факт-пакет, Markdown остаётся доступен через API |
| `GET` | `/api/analyses/{inn}` | сохранённый анализ по контрагенту (кэш между сессиями) |
| `GET` | `/api/contractors/{inn}` | факт-пакет для карточки |
| `POST` | `/api/compare` | `{inns: [...]}` → найденные контрагенты плюс списки `missing` и `invalid`; частичный результат не является ошибкой |
| `GET` | `/api/health` | статус приложения и доступность БД |

Токен подписывается HMAC с TTL из конфига. Если секрет остался значением
по умолчанию, приложение стартует, но пишет предупреждение в лог —
ломать запуск из-за незаполненного `.env` нельзя.

**История сообщений не хранит факт-пакеты.** В `messages.meta` кладётся только
ИНН и признак degraded; сам отчёт живёт в `analyses` и отдаётся через
`/api/sessions/{id}/report`. Это согласовано с §10.1, где факт-пакеты из истории
вырезаются при сборке контекста.

**Название сессии** проставляется автоматически по первому разобранному
контрагенту, если пользователь не задал своё.

## 13. Frontend

**Vite + React + TS**, компоненты только из `@alfalab/core-components`.
Next.js не используется: SSR не нужен, бэкенд — FastAPI, а библиотека
потребовала бы `"use client"` на каждом компоненте и настройки транспиляции.
Сборка — статика, раздаётся FastAPI.

Экраны: окно авторизации (логин/пароль, один пользователь) → основной экран.

Основной экран — три зоны:
* слева — список сессий с удалением, кнопка «Новая проверка»;
* центр — чат; роль анализа выбирается в настройках рядом с полем ввода;
* справа — карточка контрагента: светофор `risk_level`, отдельно ЗСК,
  плашка расхождения, выручка/прибыль за 3 года, арбитраж истец/ответчик,
  активные исполнительные производства, список факторов риска, связанные компании.

Режим сравнения — таблица N контрагентов на месте карточки.

## 14. Degraded-режим (LLM API недоступен)

Поскольку весь факт-пакет считается кодом, при недоступности LLM отдаём
**не ошибку, а детерминированный отчёт**: светофоры, все цифры, факторы риска,
расхождения и шаблонный вердикт по правилам. Без художественного текста,
с честной плашкой «ИИ-анализ временно недоступен, показаны данные отчёта».
Для демо это выглядит значительно лучше пятисотки и почти ничего не стоит.

Уровни деградации: `LLM ok` → `LLM недоступна (шаблонный отчёт)` → `БД недоступна (ошибка)`.

## 16. Порядок работ

Агент кладётся **последним, на готовые backend и UI** — так к моменту его
подключения есть куда возвращать ответ и на чём его смотреть.

**Этап 1 — фундамент (без него не поедет ничего)**
1. Схема БД + `normalize.py` + `load_data.py`.
   Проверка: счётчики строк совпадают с `data_profile.md`, в нормализованных
   колонках не осталось Extended JSON.
2. `aggregates.py` + `factpack.py`.
   Проверка: размеры обоих режимов пакета укладываются в замеры `data_profile.md`
   даже на самом крупном контрагенте.
3. `discrepancy.py`.
   Проверка: срабатывания правил совпадают с `data_profile.md`, без лишних.

**Этап 2 — приложение (backend + UI без агента)**
4. FastAPI: пользователь, сессии, сообщения, история.
5. MCP базовые инструменты над БД — проверяются напрямую, без LLM.
6. UI: окно авторизации, чат, карточка контрагента, список сессий.
   На этом шаге чат отвечает **детерминированным отчётом** (§14) — тем самым,
   что потом станет фолбэком. Приложение уже полностью рабочее и демонстрируемое.
7. Сравнение нескольких ИНН, выгрузка JSON/Markdown.

**Этап 3 — агент поверх готового приложения**
8. Коннектор LLM + промпты ролей + Structured Output.
9. Граф LangGraph, роутер, извлечение ИНН.
10. Память сессии: якорь + ручки `save_analysis` / `get_analysis` (§10.1).
11. `validator.py` + переключение фолбэка на degraded-режим.

**Этап 4 — если останется время**
12. PDF (нужен кириллический шрифт), графики, LLM-валидатор, веб-поиск,
    продвинутые MCP-инструменты.

## 17. Решено дополнительно

1. **ЗСК показываем реальный** — `GREEN` / `YELLOW` / `RED` как в данных,
   без маскировки жёлтого и красного под серый (§3.2).
2. **Пороги детектора** обоснованы на данных и вынесены в конфиг (§3.3):
   5 % выручки, 10 активных ИП при отсутствии отчётности, 10 млн ₽ абсолютных.
   Подкрутить на демо — вопрос одной переменной окружения.
3. **Авторизация базовая**: окно логина, один заведённый пользователь,
   пароль из конфига. Таблица `users` и `user_quotas` заполняются,
   чтобы задел под мультипользовательский режим и лимиты остался,
   но регистрации и восстановления пароля нет.

## 18. Соглашения по коду

* **Одна точка входа** — `app.py` с подкомандами: `serve` (FastAPI + UI),
  `mcp` (MCP-сервер), `load-data` (сид из JSON). В `docker-compose` это разные
  команды одного образа.
* **Конфигурация.** Все параметры перечислены в `config/internal_config.yaml`
  со значениями по умолчанию, включая ключи секретов с пустой строкой.
  `.env` только переопределяет значения и лежит в `.gitignore`.
  Код читает настройки **исключительно** через объект настроек,
  прямых обращений к `os.getenv` в проекте нет.
* **Таблицы** создаются через `Base.metadata.create_all` при `load-data`.
  Alembic не используется: схема фиксированная, данные перезаливаются из снапшота,
  версионировать нечего.
* **Без глобальных переменных.** Неизменяемые константы модуля допустимы;
  изменяемое состояние и тяжёлые объекты, создаваемые на импорте, — нет.
  Движок БД и настройки отдаются ленивыми фабриками (`get_engine()`, `get_settings()`
  под `lru_cache`): импорт модуля не лезет в сеть, а в тестах кэш сбрасывается.
* **Комментарии** — только там, где поведение неочевидно
  (омоглифы в кодах факторов, `$numberLong`, приоритет обрезки контекста).
  Пояснять очевидное не нужно.
* Идентификаторы и имена файлов — латиницей; русский — в текстах для пользователя
  и в редких поясняющих комментариях.
* **Compose запускается из корня репозитория** с `--project-directory .` —
  тогда и подстановка переменных, и `env_file` берутся из корневого `.env`:
  `docker compose --project-directory . -f devops/docker-compose.yml up -d db`.
  Все параметры подключения, включая порт, задаются через `.env`.
* **Снапшот в `.gitignore`.** `docs/internal_files/*.json` и `*.csv` не в репозитории —
  перед первым запуском файл нужно положить локально, иначе `load-data` упадёт
  с внятной ошибкой.
