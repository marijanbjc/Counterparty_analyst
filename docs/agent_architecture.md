# Архитектура агента

Документ описывает слой между интерфейсом и MCP: как обрабатывается один ход диалога,
что уходит в модель и что приходит обратно.

Инструменты — в `mcp_architecture.md`. Данные — в `data_profile.md`.
Общая схема системы — в `architecture.md`; расхождения с ней перечислены в §10.
Версия: 2026-09-04. Статус: черновик, к обсуждению.

---

## 1. Сценарии: что делает агент в ответ на сообщение

Всё начинается с одного детерминированного вопроса: **сколько ИНН в сообщении
пользователя**. Ответ на него задаёт сценарий целиком.

| ИНН в сообщении | Состояние сессии | Сценарий | Вызовов LLM |
|---|---|---|---:|
| 0 | ничего не разобрано | **Переспрос** | 0 |
| 0 | что-то уже разобрано | **Уточнение** | 1–2 |
| 1 | любое | **Разбор** | 1 |
| 2–10 | любое | **Сравнение** | 1 |

### 1.1. Переспрос — 0 ИНН, сессия пуста

Пользователь написал что-то, из чего ИНН не извлекается, и в сессии нет ни одного
разобранного контрагента. Отвечать не по чему.

**LLM не вызывается вообще.** Возвращается детерминированная подсказка с форматом:
ИНН — это 10 цифр для организации или 12 для предпринимателя.

Почему без модели: тратить вызов на то, чтобы переформулировать константу, незачем,
а на бесплатном тарифе каждый вызов — доля минутного лимита. Плюс это единственный
сценарий с нулевой задержкой, а он же и самый частый в начале диалога.

**Сюда же попадают запросы вне наших возможностей** — «найди подрядчика в Москве».
Поиска по базе в архитектуре нет (`mcp_architecture.md` §5), и ответ честный:
работаю по конкретному ИНН, назовите его. Инструменты выборки — предмет отдельной
итерации.

### 1.2. Уточнение — 0 ИНН, но что-то разобрано

Пользователь спрашивает про уже проверенного контрагента: «а что с судами?»,
«какая была выручка?». ИНН он не повторяет — и не должен.

Единственный сценарий, где **модель сама выбирает инструменты**. Большого факт-пакета
в контексте нет, поэтому схемы инструментов по бюджету помещаются.

Ответ — короткая реплика. **Новый отчёт не создаётся**, таблица `analyses` не трогается:
вопрос про выручку не рождает вердикт.

### 1.3. Разбор — 1 ИНН

Основной сценарий, ради которого всё строится. Код сам собирает факт-пакет и отдаёт
модели готовые числа.

Результат — полный разбор: вердикт, сводка, подробный анализ, ключевые риски.
Пишется в `analyses(inn, analysis_type)` и попадает в якорь сессии.

### 1.4. Сравнение — 2–10 ИНН

Код вызывает `compare_contractors`: сводная таблица, различия и ранжирование
считаются детерминированно. Модель их только проговаривает.

Сводного вывода «работайте с этим» не даёт ни код, ни модель — решение остаётся
за пользователем (прямое требование кейсодателя).

## 2. Ключевое решение и его обоснование

> **Мы не строим классический агентский цикл. Мы строим детерминированный конвейер
> с одним вызовом LLM на ход.**

Решение принято не из соображений вкуса, а по замерам на живом API.

### 2.1. Что измерено

Groq, `openai/gpt-oss-120b`, бесплатный тариф: **лимит 8000 токенов в минуту**.

| Блок | Токенов |
|---|---:|
| Системный промпт | 110 |
| Схемы инструментов: ядро (9) | 1 817 |
| Схемы инструментов: роль (14) | 2 826 |
| Схемы инструментов: все (24) | 4 586 |
| Факт-пакет `full` | 3 798 |
| Факт-пакет `full` без позитивных факторов и связанных компаний | 2 029 |

Схемы инструментов пересылаются **на каждой итерации** цикла. Отсюда стоимость хода:

| Вариант | Токенов | Итог |
|---|---:|---|
| Агентский цикл, 2 шага | 2 936 + 6 734 = **9 670** | **429, лимит превышен** |
| Префетч + инструменты в том же вызове | 6 734 | впритык, следующий ход через минуту |
| **Префетч без инструментов** | **3 214 замерено** | **помещается с запасом** |

Первый вариант проверен на живом API и упёрся в 429 на втором шаге.

### 2.2. Что из этого следует

**Какие данные нужны — решает код. LLM формулирует.**

Помимо экономии это снимает риск: `legal_status` попадает в контекст всегда,
а не тогда, когда модель догадается его запросить. На МАКСМАРКЕТ (ИНН 5032257375)
это разница между «низкий риск, зелёный ЗСК» и «признано банкротом, открыто
конкурсное производство».

Агентность не исчезает — она переезжает в сценарий «Уточнение», где по бюджету
помещается.

### 2.3. Что показала проверка качества

Один вызов, факт-пакет подставлен кодом, `json_schema` со `strict: true`.
Контрагент — МАКСМАРКЕТ: `riskLevel = LOW`, ЗСК зелёный, при этом банкрот.

| Проверка | Результат |
|---|---|
| JSON распарсился с первого раза | да |
| Назвал банкротство при зелёном светофоре | **да, сам** |
| Поднял вердикт до «Работать с осторожностью» | да |
| Различил действующие взыскания (54) и историю (507) | да |
| Выдуманные ИНН в ответе | нет |
| Прямое указание «работать» | нет |

Все десять чисел из ответа сверены с факт-пакетом — совпали. Единственное расхождение:
3 995 486 против 3 995 487, модель округлила рубль. Это ровно та причина, по которой
валидатор не сверяет цифры посимвольно (`mcp_architecture.md` §8.4).

╚═══╤═════════════╤══════════════════╤═══════════════╤═══════════════╝

                                       ▼
            ╔═ RATE LIMITER ═══════════════════════════════════════╗

## 4. Что получает модель

Массив сообщений собирается **по бюджету токенов, а не по числу реплик**: десять
последних сообщений — непредсказуемая величина от 200 до 20 000 токенов, потому что
среди них может оказаться развёрнутый отчёт.

```
[
  system : правила + методология + правила роли              ~110
  system : [Разобрано в этой сессии] — якорь из БД           ≤900    (кроме разбора)
  ...    : последние реплики диалога                         остаток бюджета
  user   : вопрос + факт-пакет JSON                          2 000–3 800
]
```

Приоритет при нехватке бюджета:

| Блок | Режется? |
|---|---|
| системный промпт и правила роли | никогда |
| факт-пакет текущего контрагента | никогда |
| якорь сессии | никогда |
| последние реплики диалога | первым, с самых старых |
| прошлые факт-пакеты и ответы инструментов | вырезаются целиком → «см. якорь» |

### 4.1. Якорь сессии

Компактная сводка того, что уже разобрано. Собирается **кодом** из таблицы `analyses`,
решения модели не требует, а значит не может быть забыт.

```
[Разобрано в этой сессии]
1. ООО "МАКСМАРКЕТ" (ИНН 5032257375) — вердикт: Работать с осторожностью.
   Риск LOW / ЗСК зелёный. Данные на 2026-07-30.
   ! В ЕГРЮЛ: признано банкротом, открыто конкурсное производство
   ! Формально низкий риск при 6 негативных факторах
   Выручка 2023: 116 257,9 млн ₽. Исп. производства: активных 54, всего 507.
   Полный отчёт: get_analysis("5032257375").
```

Около 180 токенов на контрагента, число контрагентов ограничено параметром
`context_anchor_max_contractors`. **Якорь всегда содержит ИНН** — поэтому после
обрезки окна модель берёт его оттуда, а не воспроизводит по памяти.

### 4.2. Когда прикладываются инструменты

| Сценарий | Инструменты | Почему |
|---|---|---|
| Переспрос | — | LLM не вызывается |
| **Уточнение** | **ядро, 9 шт., 1 817 токенов** | Большого пакета в контексте нет, помещаются |
| Разбор | — | Всё нужное код уже положил в пакет |
| Сравнение | — | Сводка посчитана кодом |

Это параметр, а не архитектура: на платном тарифе схемы можно прикладывать всегда,
и конвейер превращается в полноценный цикл без переписывания.

## 5. Что отдаёт модель

Две схемы. Выбирает **код** по сценарию, а не модель.

### 5.1. Реплика — сценарий «Уточнение»

```json
{ "answer": "Открытых дел в роли ответчика — 3. Всего 258, большинство завершены." }
```

Пишется только в `messages`.

### 5.2. Разбор — сценарии «Разбор» и «Сравнение»

Через `response_format: json_schema` со `strict: true`.

```json
{
  "answer":    "реплика в чат, 3–6 предложений",
  "verdict":   "Работать | Работать с осторожностью | Не рекомендуется",
  "summary":   "1–2 строки, идут в якорь сессии",
  "analysis":  "подробный разбор со ссылками на поля источника",
  "key_risks": ["...", "..."]
}
```

Пишется в `messages` **и** в `analyses(inn, analysis_type)`, попадает в якорь.

Ключ таблицы — `(inn, analysis_type)`, а не `session_id`: повторный запрос той же
компании в новой сессии поднимает готовый анализ вместо пересчёта.

### 5.3. Особенности модели

* **Поле `reasoning` присутствует в каждом ответе** — модель reasoning-типа.
  Отсекать при парсинге: ни в БД, ни пользователю оно не идёт. Проверено на всех вызовах.
* `json_schema` со `strict: true` поддержан и отработал с первого раза, но фолбэк
  на повторный запрос при невалидном JSON обязателен.
* `temperature: 0.0` — воспроизводимость важнее разнообразия формулировок.

## 6. Компоненты

| Компонент | Отвечает за | LLM? |
|---|---|---|
| **Router** | `inn.extract`, `areas_for_text`, выбор сценария | нет |
| **Prefetch** | вызов `get_contractor_full` / `compare_contractors` кодом | нет |
| **Context builder** | сборка сообщений по бюджету токенов, якорь сессии | нет |
| **Rate limiter** | учёт TPM, сериализация вызовов, backoff по 429 | нет |
| **LLM connector** | Groq, отсечение `reasoning`, `json_schema` + фолбэк | **да** |
| **Tool dispatcher** | только на уточнении: гейт белого списка ИНН, вызов MCP | нет |
| **Validator** | три инварианта, один повтор при провале | нет |
| **Persister** | `messages`, `analyses`, `session_analyses`, квота, якорь | нет |
| **Degraded** | 429 или отказ LLM → детерминированный отчёт | нет |

Из девяти компонентов LLM участвует ровно в одном. Это и есть принцип
«код считает, модель формулирует» в исполнении.

### 6.1. Лимитер — штатный компонент, а не подстраховка

На бесплатном тарифе 429 прилетает регулярно, а не в исключительных случаях.
Лимитер ведёт скользящее окно израсходованных за минуту токенов, сериализует
вызовы и при исчерпании ждёт до освобождения окна вместо мгновенной ошибки.

### 6.2. Деградация

Уровни: `LLM ok` → `LLM недоступна или лимит` → `БД недоступна`.

При отказе LLM отдаём **не ошибку, а детерминированный отчёт** из `core/report.py`:
светофоры, все цифры, факторы риска, расхождения и шаблонный вердикт. Без
художественного текста, с честной плашкой «ИИ-анализ временно недоступен».

## 7. Правила промпта

Выведены из `mcp_architecture.md` §2 и уточнены по результатам живого теста.

1. Использовать **только** переданные данные. Нет в них — «таких данных в отчёте нет».
2. Не считать самому: все производные значения уже посчитаны.
3. `null` — данных нет, это **не ноль**. `"not_applicable"` — поле неприменимо к ИП.
4. Вердикт строится на `verdict_basis.risk_level`. Оценка ЗСК упоминается отдельно
   и с вердиктом не смешивается.
5. При непустых `discrepancies` или `legal_status.severity = "critical"` — сказать
   об этом **обязательно**, даже когда светофор зелёный.
6. Различать действующие взыскания и историю: это разные величины, разрыв доходит
   до двух порядков.
7. Про арбитраж говорить только агрегатами; отдельные дела не описывать — их нет в источнике.
8. Указывать дату актуальности `as_of`.
9. Не давать указаний «работать» или «не работать»: подсвечивать риски и аккуратно
   рекомендовать. Решение принимает пользователь.
10. Не раскрывать полноту базы: никаких «известно N из M», долей заполненности, размера базы.

### 7.1. Три правки по итогам теста

Модель в целом соблюдала правила, но три вещи вылезли:

| Что | Пример из теста | Правка |
|---|---|---|
| Имена полей протекли в текст для пользователя | «legal_status.severity = critical», «Discrepancies подтверждают» | Ссылки на поля допустимы в `analysis`, запрещены в `answer` |
| Латиница вместо кириллицы | «ZSK-оценка» | Закрепить написание «ЗСК» |
| Доля вместо процентов | «коэффициент 0,0109» | Доли переводить в проценты |

## 8. Оркестрация: почему без LangGraph

`architecture.md` §10 закладывает LangGraph. По итогам проработки предлагается
обычный конвейер. Разбор решения — чтобы его можно было пересмотреть осознанно.

### 8.1. Что из LangGraph нам нужно

| Возможность | Нужна? | Почему |
|---|---|---|
| Условные переходы | почти нет | Сценарий определяет роутер **до** графа |
| Чекпойнты состояния | нет | Состояние в Postgres, ход stateless |
| Прерывания, human-in-the-loop | нет | Уточнение у пользователя — новый HTTP-запрос |
| Параллельные ветки | пока нет | Появятся, если суб-агенты станут LLM-разборами |
| Стриминг событий по узлам | **да** | Сигнал «идёт работа» |
| Ретраи на узле | да, но | Нужен ретрай по TPM — это лимитер, а не политика узла |

### 8.2. Минусы в нашем случае

1. **Вес зависимостей.** Тянет `langchain-core` и цепочку за ним, а в venv уже
   разруливался конфликт `fastapi` / `starlette` / `fastmcp`.
2. **Экосистема не используется.** К Groq ходим голым `httpx`: нужно отсекать
   `reasoning` и управлять `json_schema`. Берём граф, но не то, ради чего его берут.
3. **Отладка длиннее.** Исключение внутри узла всплывает через машинерию графа.
4. **Состояние общим словарём** менее явно, чем типизированные аргументы.
5. **Главная фича не задействована** — динамическая маршрутизация разрешается
   роутером за миллисекунду до старта.

### 8.3. Как без него

```python
def handle_turn(session_id, message, role) -> TurnResult:
    plan = router.plan(message, session_id)
    if plan.kind == "clarify":
        return TurnResult(answer=plan.hint)          # LLM не вызываем

    facts = prefetch.collect(plan)
    ctx = context.build(session_id, plan, facts)

    with limiter:
        reply = llm.complete(ctx, schema_for(plan.kind))

    if not validator.check(reply, ctx).passed:
        reply = llm.complete(ctx.with_error(...), schema_for(plan.kind))

    persist.save(session_id, plan, reply)
    return reply
```

Порядка 310 строк: роутер ~40, префетч ~30, контекст ~60, коннектор ~80,
диспетчер ~50, сохранение ~50. Валидатор уже написан. Стадии наружу — обычный
колбэк или генератор, ~20 строк.

### 8.4. Когда вернуться к вопросу

Если суб-агенты `run_focused_analysis` станут настоящими LLM-разборами и их
понадобится гонять параллельно. Тогда fan-out руками неприятен, и граф себя оправдает.

**Решение обратимо:** узлы конвейера ровно те же, на LangGraph переносится
обвязка, а не логика.
