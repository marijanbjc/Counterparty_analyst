# MCP-сервер: каталог инструментов

Документ описывает инструменты, которые агент вызывает через MCP (FastMCP).
Общая архитектура системы — в `architecture.md`, разбор исходных данных — в `data_profile.md`.
Версия: 2026-09-04. Статус: утверждено, к реализации.

Разделы 4, 7 и 8 — назначение инструментов: по конкретному ИНН, по выборке
контрагентов, продвинутые. Раздел 9 — спецификация для реализации: описания
для FastMCP, вход и выход. Раздел 10 — какие инструменты попадают в промпт
на конкретном шаге и почему не все сразу.
Свободного поиска по базе в архитектуре нет, обоснование в §5.

---

## 1. Назначение

Инструмент — тонкая обёртка над SQL. Он **считает и отдаёт факты**, не интерпретирует их.
Вся арифметика, агрегация и пороги — в детерминированном Python-коде; LLM получает
готовые числа и только формулирует текст. Это прямое следствие главного критерия
оценки решения: «не выдумывает информацию, использует только входные данные»
(`architecture.md` §1).

Описание каждого инструмента — часть промпта модели. Поэтому в описаниях
**явно указываются границы данных**: чего в источнике нет, и что означает пустое значение.

## 2. Общие соглашения — контракт всех инструментов

### 2.1. Неизвестный ИНН

Единый структурированный отказ. База закрыта: ИНН вне неё — всегда ошибка, а не пустой ответ.

```json
{"found": false, "reason": "not_in_database", "inn": "5029069960",
 "hint": "Контрагента с таким ИНН в базе нет. Переспросите ИНН у пользователя."}
```

Отказ **не перечисляет** известные ИНН — иначе на каждой опечатке модели вываливается
содержимое базы, и она начинает брать «любой подходящий» ИНН из списка.

Отдельная причина `reason: "invalid_inn"` — если ИНН не прошёл проверку контрольного
разряда (`core/inn.py`): 10 знаков для организации, 12 для предпринимателя.

### 2.2. Три разных вида «нет значения»

Смешивать их запрещено — на этом ломается главная метрика.

| Маркер | Смысл | Пример |
|---|---|---|
| `null` | данных нет в источнике | `profit: null` — прибыль не раскрыта |
| `"not_applicable"` | поле неприменимо к этому типу лица | КПП у предпринимателя |
| блок отсутствует / `available: false` | целого раздела в отчёте нет | `finReports` у 33 контрагентов |

**Ноль вместо отсутствия запрещён.** `profit: 0` и `profit: null` — разные утверждения:
первое означает «сработал в ноль», второе «неизвестно».

Каждый инструмент возвращает список `missing` с именами полей, по которым данных нет.
Модель инструктируется: если запрошенного нет — единственный допустимый ответ
«таких данных в отчёте нет».

### 2.3. Текущее отдельно от исторического

Самая частая ошибка интерпретации. По базе: активных исполнительных производств
**213 из 3873**, остальное закрыто, самое старое — 2011 год. Открытые арбитражи есть
у 24 контрагентов, у остальных дела завершены. У ЛЕ МОНЛИД разрыв на два порядка:
254,5 млн ₽ за всю историю против 1,6 млн ₽ действующих.

Инструмент, отдающий одно число, заставит агента пугать пользователя взысканием
2014 года. Поэтому **каждый юридический и долговой инструмент возвращает две пары
счётчиков** в отдельных полях: `active_*` / `total_*`, `pending_*` / `total_*`.
Суммировать их в промпте модель не должна и не может — сумма уже посчитана кодом.

### 2.4. Фактор едет вместе с фактом

Блок `reputationalRisks` содержит готовые человекочитаемые формулировки банка,
размеченные полем `chapter`. Каждый предметный инструмент возвращает **свои** факторы
рядом со своими цифрами:

| chapter | Уезжает в инструмент |
|---|---|
| `finance` | `get_financials`, `get_balance_sheet`, `get_liabilities` |
| `execproc` | `get_execution_proceedings` |
| `arbitr` | `get_arbitration` |
| `reestrs`, `manager` | `get_fns_flags` |
| `okved` | `get_activity` |
| `relatedComp` | `get_affiliations` |
| `license` | `get_licenses` |
| `site`, `filials` | `get_basic_info` |

Модель получает готовую формулировку банка прямо рядом с числом, которое она объясняет,
и не сочиняет интерпретацию сама.

Это заодно закрывает дыру в текущем коде: `core/roles.py` покрывает 5 разделов из 10,
и `okved` (25 негативных факторов), `relatedComp`, `license`, `site`, `filials`
сейчас не попадают ни в одну роль, кроме «Общий».

### 2.5. Что не раскрывается пользователю

Агент отвечает по той базе, которую знает, и не комментирует её полноту.
Наружу не выходят: доля заполненности полей, размер базы, формулировки «известно N из M».
Ни в ответе модели, ни в поле ответа инструмента.

Отсутствие данных **по конкретному запрошенному контрагенту** сообщать обязательно.
Граница проходит по объекту высказывания: «в отчёте не указан сайт компании» — можно,
«у N компаний нет сайта» — нельзя.

### 2.6. Объём ответа

Тяжёлые массивы никогда не отдаются целиком — только агрегат плюс топ-N.
Максимальный отчёт в источнике — 238 тыс. символов (~95 тыс. токенов, ЛЕ МОНЛИД
с 1744 производствами). Ни один инструмент не имеет права отдать это в контекст.

### 2.7. Формат

* Суммы — целые рубли, число, без форматирования. Округление и «млн ₽» — задача слоя представления.
* Даты — ISO `YYYY-MM-DD`.
* Каждый ответ содержит `as_of` — дату отчёта (`reportDate`). Данные не «сегодняшние»:
  снапшот датирован концом июля — августом 2026.
* Извлечение `$date` / `$numberLong`, строк-чисел и кириллических омоглифов в кодах
  выполнено на загрузке (`core/normalize.py`). В инструменты приходят чистые типы.

## 3. Ограничения данных, влияющие на весь каталог

### 3.1. Предприниматели — почти пустая оболочка

25 из 100 контрагентов — ИП. У них заполнено только:

| Есть у всех 25 ИП | Есть частично | **Нет ни у одного ИП** |
|---|---|---|
| ИНН, ОГРНИП, наименования | связанные компании (9) | адрес, телефон, e-mail, сайт |
| дата регистрации, возраст | исп. производства (6) | финансовая отчётность |
| ОКВЭД | арбитраж по годам (5) | учредители, уставный капитал, КПП |
| оба светофора, факторы риска | проверки (3) | налоговый режим, размер бизнеса, лицензии, закупки |

Для ИП половина каталога обязана вернуть `not_applicable` (КПП, учредители, УК)
либо `available: false` (финансы). Различать эти два случая критично: первое —
«у этого типа лица такого не бывает», второе — «в отчёте нет».

Предприниматели также **не попадают в географическую выборку** — адреса нет ни у одного.
Это техническое следствие, а не факт о контрагенте, и наружу оно не выходит (§2.5).

### 3.2. Чего в источнике нет вовсе

* **Конкретных судебных дел** — только агрегаты по годам и статусам. Ни номеров дел,
  ни сторон, ни предметов спора. Инструмента «список дел» не существует и не будет.
* **Численности персонала** — `staff` пуст у всех 100.
* **Связного графа контрагентов** — из 249 рёбер `relatedCompanies` внутрь базы ведут 2.
* **Истории смены руководителя** — только текущий и дата его назначения.

### 3.3. `massOkved` не воспроизводим и воспроизводить не нужно

Флаг ставится не по количеству кодов у компании, а по попаданию в «серый» список
ОКВЭД, которые по статистике ФНС чаще выбирают фирмы-однодневки (пояснение кейсодателя).

Проверено на данных: у помеченных 21–121 код, но и у 15 непомеченных 21–29 кодов —
чистой границы по количеству нет. Названные кейсодателем `42.90` и `82.9`
в базе не встречаются вообще, `82.99` есть у 6/25 помеченных и 9/75 непомеченных.
Ни один код не разделяет выборки.

**Решение: флаг берём готовым и показываем с формулировкой банка как есть.**
Своей интерпретации не строим, порог не подбираем. Формулировка банка сама
задаёт вес: «повод насторожиться, не более».

### 3.4. Светофоров два, и они расходятся

`riskLevel` — `LOW` / `MEDIUM` / `HIGH` / `UNKNOWN`, четыре состояния (зелёный,
жёлтый, красный, серый). `zskRiskLevel` — оценка «Знай своего клиента»,
в интерфейсе **два состояния: зелёный и серый**; `YELLOW` и `RED` показываются серым
(уточнение кейсодателя). Флаг `zsk_mask_yellow_red` в конфиге отвечает за это,
сейчас стоит в `false` — требует переключения.

Вердикт строится на `riskLevel`. ЗСК упоминается отдельно. Расхождения помечает
детектор `core/discrepancy.py`, инструменты их не считают.

## 4. Каталог инструментов

### 4.1. Откуда берётся ИНН

**Инструмента поиска контрагента по названию нет.** Единственный источник ИНН —
сообщение пользователя. ИНН из сообщения извлекается регулярным выражением
и проверяется по контрольному разряду (`core/inn.py`): 10 знаков для организации,
12 для предпринимателя. Не извлеклось или не прошло проверку — **агент переспрашивает
пользователя**, а не подбирает кандидата.

**Почему так.** Инструмент вида `resolve_contractor(query)` был спроектирован
и отвергнут: он возвращает модели названия и ИНН реальных компаний на любой
неточный запрос, и через ответ модели состав базы утекает пользователю.
Цена отказа — теряется один из четырёх слоёв защиты от галлюцинаций
(`architecture.md` §9.1, слой 3 «поиск вместо набора цифр»). Компенсируется тем,
что модель вообще не имеет способа получить ИНН иначе, чем из реплики пользователя
или из ответа инструмента, и **белым списком ИНН сессии** (слой 4), значение
которого после этой правки возрастает.

Множество легальных ИНН сессии пополняется из трёх источников:
сообщения пользователя, поля `related_inn` в ответе `get_affiliations`,
результата `find_similar_contractors` (§7.2). Вызов любого `get_*` с ИНН
вне множества отклоняется.

### 4.2. Профиль и правоспособность

#### `get_basic_info(inn)`

**О чём.** Паспорт контрагента: кто это, где сидит, сколько лет на рынке, с кем
разговаривать. Первый инструмент в любом сценарии — задаёт рамку для всего остального.

| Поле | Тип | Смысл | Покрытие |
|---|---|---|---|
| `short_name`, `full_name` | str | наименования | 100 |
| `inn`, `ogrn`, `okpo` | str | идентификаторы; ОГРН 13 знаков у ЮЛ, 15 (ОГРНИП) у ИП | 100 |
| `kpp` | str \| not_applicable | у предпринимателей не существует | 75 |
| `entity_kind` | enum | `organization` / `sole_proprietor` | 100 |
| `registered`, `age_years` | date, int | дата регистрации и возраст | 100 |
| `company_size` | str | микро / малое / среднее / крупное | 59 |
| `address`, `region` | str | адрес и вырезанный из него регион | 75 |
| `phones[]` | str[] | все номера, а не первый | 29 |
| `email`, `website` | str | контакты | 35 / 11 |
| `auth_person` | obj | руководитель: `{name, position, since}` | 75 |
| `tax_systems[]` | str[] | ОСНО (51) / УСН (24) | 75 |
| `branches` | obj | количество и адреса филиалов | 2 |
| `staff` | null | **пусто у всех 100**, всегда «нет данных» | 0 |
| `factors[]` | obj[] | факторы `chapter` = `site`, `filials` | — |

**Вопросы бизнеса:** «Кто это вообще, где он находится, давно ли работает,
кому звонить и с кем подписывать». Возраст особенно значим: **29 контрагентов
базы моложе двух лет**, из них 12 зарегистрированы в текущем году.

---

#### `get_legal_status(inn)` — **новый, всегда попадает в факт-пакет**

**О чём.** Проверка правоспособности: существует ли юридическое лицо, не идёт ли
процедура его прекращения. Самый важный инструмент каталога и единственный,
который **не отдаётся на усмотрение модели** — он подмешивается в факт-пакет
всегда, потому что банкротство нельзя ставить в зависимость от того, догадается
ли модель его запросить.

| Поле | Тип | Смысл |
|---|---|---|
| `status` | str | `CURRENT` — у всех 100 контрагентов базы |
| `status_date` | date | дата присвоения статуса |
| `status_reason` | str \| null | **текст причины из ЕГРЮЛ** |
| `severity` | enum | `critical` / `attention` / `none` — градация причины |
| `factors[]` | obj[] | метки банкротства и ликвидации (`liquidationStatus`) |

Градация `severity` — детерминированная, по коду причины:

| Причина | severity | Смысл |
|---|---|---|
| признано банкротом, открыто конкурсное производство | `critical` | лицо в процедуре банкротства |
| решение о предстоящем исключении из ЕГРЮЛ | `critical` | лицо на грани исключения |
| изменение места нахождения | `attention` | маркер грядущих изменений |
| уменьшение уставного капитала | `attention` | маркер грядущих изменений |
| причины нет | `none` | — |

Градация «критично / проверить» согласована с кейсодателем: «часто это маркеры
грядущих изменений — переезд адреса реже, снижение УК чаще — проверить».

**Вопросы бизнеса:** «Он вообще живой и правоспособный? Не банкрот ли?»

**Почему инструмент обязателен.** `status` равен `CURRENT` у всех 100 контрагентов,
то есть по нему банкрот неотличим от здоровой компании. Реальная информация лежит
в `status_reason`, которое сейчас грузится в БД и **не выходит ни в факт-пакет,
ни в детектор расхождений**. В базе три таких случая, и два из них показательны:

| Компания | ИНН | Причина | Светофор |
|---|---|---|---|
| ООО «МАКСМАРКЕТ» | 5032257375 | признано банкротом, открыто конкурсное производство | **LOW / GREEN** |
| ООО «РАДО АЛАТЫРЬ КС» | 2100006761 | предстоящее исключение из ЕГРЮЛ | **LOW / GREEN**, ноль негативных факторов |
| ООО «БИЛД-ЮГ» | 2311304742 | изменение места нахождения | LOW / GREEN |

**Следствие для `core/discrepancy.py`:** нужно новое правило `green_but_status_reason` —
`severity = critical` при зелёном светофоре.

#### `get_fns_flags(inn)` — новый

**О чём.** Метки налоговой и метки по руководителю: чем ФНС пометила контрагента
в своих реестрах. Отдельная плоскость от `get_legal_status`: там жизненный цикл
юрлица, здесь — репутационные отметки государства.

**Возвращает** по каждой метке `{code, present, name, severity}`, где `name` —
готовая формулировка банка, а `present` явно различает «метка есть» и «метки нет»
(в источнике оба случая приходят как факторы, негативный и позитивный).

| Метка | Негативна у | Смысл |
|---|---|---|
| `massAddress` | 13 | адрес массовой регистрации |
| `fnsBlocking` | 9 | действующая блокировка счетов по постановлению ФНС |
| `invalidAddress` | 3 | реестр фиктивных адресов |
| `invalidRegistrationData` | 3 | недостоверные регистрационные данные |
| `massAuthpersons` | 2 | массовый директор или учредитель |
| `invalidAuthpersonsData` | 1 | номинальный руководитель |
| `liquidationStatus` | 1 | реестр организаций в процедуре банкротства |
| `taxArrears`, `taxReporting`, `dishonestProvider`, `disqualifiedAuthpersons` | 0 | налоговые долги, сдача отчётности, недобросовестный поставщик, дисквалификация |

**Градация.** Блокировка счетов подаётся как **`attention`, а не как красный флаг** —
прямое указание кейсодателя: «в практике это частый кейс, краткосрочные блокировки
контрагенты чаще не расценивают как красный флаг, банк и ФНС обязаны по требованиям
регулятора». Реестры фиктивности и номинальности — `critical`.

**Вопросы бизнеса:** «Налоговая его как-то метит? Деньги до него вообще дойдут,
если счёт заблокирован? Это реальная контора или адрес массовой регистрации?»

#### `get_ownership(inn)`

**О чём.** Кто владеет компанией и чем отвечает. Для предпринимателя — целиком
`not_applicable`: у ИП по природе нет ни учредителей, ни уставного капитала.

| Поле | Тип | Смысл | Покрытие |
|---|---|---|---|
| `share_capital` | int \| not_applicable | уставный капитал, ₽ | 71 |
| `cofounders[]` | obj[] | `{name, inn, amount, share, date_from, active}` | 92 записи |
| `auth_person` | obj | руководитель и дата назначения | 75 |
| `director_is_sole_founder` | bool | директор = единственный учредитель | 46 |
| `factors[]` | obj[] | факторы `chapter` = `manager` | — |

**Вопросы бизнеса:** «Кто за ним стоит и чем он реально отвечает». Уставный капитал
показателен: **у 32 из 71 организации он минимальный, 10 000 ₽**, при медиане 12 000 ₽
и максимуме 5,98 млрд ₽. Совмещение директора и единственного учредителя (46 компаний)
само по себе не риск, но лишает контрагента внутреннего контроля.

**Примечание.** Истории смены руководителя в источнике нет — только текущий
и дата его назначения. Утверждать «директор менялся N раз» нельзя.

### 4.3. Финансы

Общее: финансовая отчётность есть у **67 контрагентов**, все из них — организации;
у 25 ИП отчётности нет ни у одного. Это 194 годовых отчёта за 2023, 2024 и 2025 годы.
Заполненность строк резко неравномерна, и это определяет разбиение на четыре
инструмента: у баланса покрытие 100 %, у прибыли — 41 %.

#### `get_financials(inn, year_from?, year_to?)`

**О чём.** Отчёт о финансовых результатах: сколько выручил и сколько заработал.

| Поле | Тип | Смысл | Покрытие |
|---|---|---|---|
| `available` | bool | есть ли отчётность вообще | 67 из 100 |
| `years[]` | obj[] | `{year, proceeds, profit}` по годам | 194 отчёта |
| `proceeds` | int \| null | выручка, ₽ | 169 / 194 (87 %) |
| `profit` | int \| null | **прибыль или убыток** (может быть отрицательной), ₽ | 79 / 194 (41 %) |
| `trend` | obj | `{proceeds, profit}`: `growing` / `flat` / `declining`, считает код | — |
| `factors[]` | obj[] | факторы `chapter` = `finance`, в том числе готовая формулировка про убыток | — |

**Вопросы бизнеса:** «Он растёт или падает? Зарабатывает или в убытке? Какого он
масштаба — потянет мой объём?»

**Примечания.** Убыток в базе у 7 компаний (13 годовых отчётов). Прибыль не раскрыта
более чем в половине отчётов — `profit: null` здесь встречается чаще, чем значение,
и путать его с нулём нельзя. Тренд считается кодом по правилу «изменение более 5 %»,
модель тренды не выводит.

#### `get_balance_sheet(inn, year?)`

**О чём.** Что у контрагента есть: активы и собственный капитал. Отвечает на вопрос
об обеспеченности, в отличие от `get_financials`, который отвечает про оборот.
Самый полно заполненный финансовый блок — валюта баланса есть во всех 194 отчётах.

| Поле | Смысл | Покрытие |
|---|---|---|
| `total_assets` | валюта баланса, ₽ | 194 |
| `net_assets` (`capitals`) | **собственный капитал / чистые активы** | 191 |
| `current_assets` | оборотные активы | 97 |
| `stocks` | запасы | 154 |
| `receivables` | дебиторская задолженность | 182 |
| `bankroll` | денежные средства | 190 |
| `uncurrent_assets` | внеоборотные активы | 66 |
| `fixed_assets` | основные средства | 120 |
| `negative_net_assets` | флаг: чистые активы отрицательны | 5 в последнем году |

**Вопросы бизнеса:** «Есть ли у него что-то за душой? Чем он обеспечен, если дойдёт
до взыскания? Сколько живых денег на счетах против дебиторки?»

**Примечания.** Отрицательные чистые активы — обязательства превышают активы —
в последней отчётности у 5 контрагентов, за все годы у 10. Все пять зелёные по ЗСК:

|---|---|---:|---|
| ООО «ДОМ НА МОЙКЕ» | 7826131151 | −1 814 055 000 ₽ | UNKNOWN / GREEN |
| ООО «ТЕТРАДОМ» | 9714038662 | −29 564 000 ₽ | LOW / GREEN |
| ООО «САВА» | 6731007348 | −8 388 000 ₽ | LOW / GREEN |
| ООО «КАРТЕЛЬ „МОСТ“» | 7449088645 | −300 000 ₽ | LOW / GREEN |
| ООО «РАДО АЛАТЫРЬ КС» | 2100006761 | −14 000 ₽ | LOW / GREEN |

Кейсодатель прокомментировал прямо: «Светофор — комплаенс-оценка, она не всегда

#### `get_liabilities(inn, year?)`

**О чём.** Кому и сколько контрагент должен. Только пассив-обязательства, без активов
и без капитала — они в `get_balance_sheet`.

| Поле | Смысл | Покрытие |
|---|---|---|
| `total_liabilities` | итог пассивов, ₽ | 194 |
| `accounts_payable` | **кредиторская задолженность** — долги поставщикам | 184 |
| `borrowed_funds` | заёмные средства — кредиты и займы | 87 |
| `short_term_total` | краткосрочные обязательства (до года) | 87 |
| `long_term_total` | долгосрочные обязательства | 59 |
| `long_term_others` | прочие долгосрочные | 42 |

**Вопросы бизнеса:** «Сколько он должен и кому — банкам или таким же поставщикам,
как я? Долги короткие или длинные? Если он платит поставщикам с задержкой,
я стану следующим в очереди».

**Примечания.** Соотношение кредиторки к заёмным средствам показывает, за чей счёт
живёт компания: банковские деньги против товарного кредита поставщиков.
Само соотношение считает код, не модель.

#### `get_financial_ratios(inn)`

**О чём.** Готовые финансовые коэффициенты из отчёта. **Свои коэффициенты не считаем** —
решение по проекту. Нет блока `coefficient` — ответ «нет данных», а не расчёт по балансу.

Есть у **19 контрагентов**, за один год каждый (2025 — 13, 2024 — 5, 2023 — 1).

| Коэффициент | Что означает | Как читать | Диапазон в базе |
|---|---|---|---|
| `sustainability` | финансовая устойчивость — доля устойчивых источников (собственный капитал и долгосрочные обязательства) в активах | чем выше, тем меньше зависимость от коротких денег; отрицательное значение = капитал «проеден» | −0,95 … 0,88, медиана 0,33 |
| `solvency` | платёжеспособность — способность покрыть обязательства имеющимися средствами | около и выше 1 — обязательства покрыты; ниже 1 — не покрыты | 0,38 … 1,70, медиана 1,07 |
| `profitability` | рентабельность, % — сколько прибыли приносит рубль выручки | отрицательное = убыточная деятельность | −106,2 … 57,2, медиана 4,2 |

**Вопросы бизнеса:** «Он устойчив по меркам нормальной компании или живёт в долг?»

**Открытый вопрос.** Точные формулы банк в спецификации не раскрыл. Трактовки выше —
общепринятые и согласуются с наблюдаемыми диапазонами, но **их нужно подтвердить
у кейсодателя** до того, как они попадут в текст пользователю. До подтверждения
инструмент отдаёт значение и название, без нормативной оценки «хорошо / плохо».

#### `get_debt_burden(inn)` — новый

**О чём.** Отвечает на вопрос, который не отвечает ни один другой инструмент:
**эти долги для него критичны или в пределах погрешности?** Соотносит текущую
долговую нагрузку с масштабом бизнеса.

Реализует методику, названную кейсодателем прямым текстом: «в практике объёмы ИП
и арбитражей соотносятся с объёмами чистых активов, и по сопоставлению данных
можно понять, критичны или нет эти долги».

| Поле | Смысл |
|---|---|
| `current_debt` | активные исполнительные производства + открытый арбитраж как ответчик, ₽ |
| `debt_parts` | разбивка: `{execproc_active, arbitration_pending_defendant}` |
| `net_assets` | чистые активы последнего года, ₽ |
| `revenue` | выручка последнего года, ₽ |
| `debt_to_net_assets` | доля долга от чистых активов; `null` если капитал ≤ 0 или отчётности нет |
| `debt_to_revenue` | доля долга от выручки |
| `basis` | `net_assets` / `revenue` / `absolute` — на чём построена оценка |
| `comparable` | bool — есть ли с чем соотносить |

**Вопросы бизнеса:** «Взыскание на 30 млн ₽ — это для него катастрофа или мелочь?»
Один и тот же абсолютный порог непригоден: 10 млн ₽ для микропредприятия критичны,
для компании с выручкой 116 млрд ₽ — погрешность.

**Что даёт на реальных данных.** Пять контрагентов с текущим долгом выше собственного
капитала, четыре из них зелёные:

| Компания | Текущий долг / чистые активы | Светофор |
|---|---:|---|
| ООО ЛПК «САМЗА» | 1367 % | LOW / GREEN |
| ООО «ГДК» | 500 % | LOW / GREEN |
| ООО «РЕГИОН-ПРОЕКТ» | 296 % | LOW / GREEN |
| АССОЦИАЦИЯ СРО «СОМ» | 147 % (1,24 млрд ₽) | UNKNOWN / GREEN |
| ООО «ОРТУС» | 104 % | MEDIUM / YELLOW |

**Обработка отсутствующей базы сравнения.** Если отчётности нет (40 контрагентов
без выручки), соотносить не с чем — инструмент возвращает `comparable: false`,
`basis: "absolute"` и абсолютные суммы. Придумывать оценку в этом случае запрещено.
Таких случаев с ненулевым текущим долгом четыре, включая ЛЕ МОНЛИД (71,2 млн ₽
текущего долга при отсутствующей отчётности).

### 4.4. Суды и взыскания

#### `get_arbitration(inn, year_from?, year_to?)`

**О чём.** Арбитражные споры — **только агрегаты**. Конкретных дел в источнике нет:
ни номеров, ни сторон, ни предметов спора. Инструмент объявляет это явно полем
`granularity`, чтобы модель не пыталась описывать отдельные дела.

| Поле | Смысл |
|---|---|
| `granularity` | всегда `"aggregates_only"` — маркер для модели |
| `total_count`, `total_amount` | из `commonCount` / `commonAmount` |
| `as_defendant` | `{count, amount, pending_count, pending_amount}` — **ответчик** |
| `as_plaintiff` | `{count, amount, pending_count, pending_amount}` — **истец** |
| `by_year[]` | `{year, plaintiff_count, plaintiff_amount, defendant_count, defendant_amount}` |
| `factors[]` | факторы `chapter` = `arbitr` |

**Вопросы бизнеса:** «Он судится или с ним судятся? Это прямо сейчас или история?
На какие суммы?» Роль стороны меняет смысл радикально: истец взыскивает свои деньги,
ответчик — рискует не рассчитаться со мной.

**Примечания.**
* `pending` — **открытые дела**, текущий риск, в отличие от завершённых. Открытые
  есть у 24 контрагентов. У СРО «СОМ» открытых требований на 1,24 млрд ₽.
* **Стороны не суммируются в общий счётчик.** У ЛЕ МОНЛИД `commonCount` = 1525,
  а истец (1049) плюс ответчик (439) дают 1488 — 37 дел без классификации стороны.
  Общее число берётся только из `commonCount`, складывать стороны запрещено.
* Данные по годам: 2023–2026, 97 строк у 44 контрагентов.
* В источнике сторона ответчика записана с опечаткой — `defandant`. Нормализация
  на загрузке, наружу выходит `defendant`.

---

#### `get_execution_proceedings(inn, active_only=true, limit=5)`

**О чём.** Исполнительные производства — приставы уже взыскивают. Это следующая
стадия после суда и более тревожный сигнал, чем сам спор.

Полный список не отдаётся никогда: 3873 записи в базе, у одного контрагента до 1744.

| Поле | Смысл |
|---|---|
| `active`, `active_amount` | **действующие** производства: количество и сумма |
| `total`, `total_amount` | за всю историю |
| `top[]` + `top_scope` | до `limit` крупнейших: `{number, date, amount}`; scope говорит, только действующие там или все |
| `by_year` | распределение по годам возбуждения |
| `factors[]` | факторы `chapter` = `execproc` |

**Вопросы бизнеса:** «С него уже взыскивают? Сколько и давно ли? Это разовая история
или он хронически не платит?» Динамика по годам отвечает на последний вопрос:
по базе производства растут с 3 записей в 2011 году до 938 в 2025.

**Примечания.** Разрыв между историей и текущим состоянием огромен: 213 активных
из 3873. Отдавать одну сумму нельзя (§2.3). Суммы приходят строками (`"517235.54"`),
приведение — на загрузке.

### 4.5. Деятельность и допуски

#### `get_activity(inn)`

**О чём.** Чем контрагент занимается по ЕГРЮЛ и профильна ли для него моя задача.

| Поле | Смысл | Покрытие |
|---|---|---|
| `main_okved` | `{code, description}` — основной вид деятельности | 100 |
| `okved_count` | всего кодов | медиана 17, максимум 121 |
| `by_division[]` | группировка прочих кодов по разделам ОКВЭД с количеством | 2228 кодов всего |
| `mass_okved_flag` | bool + **готовая формулировка банка**, без своей интерпретации | 25 |
| `factors[]` | факторы `chapter` = `okved` | — |

**Вопросы бизнеса:** «Он профильный под мой заказ или строительство у него
двадцать восьмым пунктом? Не выглядит ли он фирмой на все руки?»

**Примечания.** Полный список кодов не отдаётся — у одного контрагента их 121.
Отдаётся основной код плюс группировка по разделам. Про `mass_okved_flag` см. §3.3:
критерий не воспроизводим, флаг и его текст берутся готовыми.

---

#### `get_licenses(inn)`

**О чём.** Разрешительные документы: есть ли законный допуск к заявленной работе.
Есть у 9 контрагентов, 14 лицензий.

**Возвращает:** `count`, `items[]` из `{number, name, issuing_authority, issue_date, end_date, status}`.
Статусы в базе: `INDEFINITE` (бессрочная) — 12, `ACTIVE` — 2. Плюс факторы `chapter` = `license`.

**Вопросы бизнеса:** «У него вообще есть право этим заниматься? Лицензия ещё действует?»
Особенно значимо там, где деятельность лицензируема: в базе это эксплуатация
взрывопожароопасных и химически опасных производственных объектов.

**Примечание.** Отсутствие лицензий в отчёте **не означает** работу без лицензии —
у большинства видов деятельности её и не требуется. Инструмент возвращает `count: 0`,
и модель не имеет права трактовать это как нарушение.

#### `get_inspections(inn)`

**О чём.** Государственный надзор: кто проверял, когда и чем закончилось.
Есть у 30 контрагентов, 343 записи.

| Поле | Смысл |
|---|---|
| `total` | всего проверок |
| `by_result` | `{violation_not_detected, unknown_result, canceled}` |
| `by_form` | по видам: предостережение, профилактический визит, выездная, инспекционный визит, документарная |
| `authorities[]` | надзорные органы с количеством проверок |
| `period` | первая и последняя даты |
| `recent[]` | последние N записей `{form, authority, start_date, end_date, status}` |

**Вопросы бизнеса:** «Его проверяли? Находили нарушения? Кто им интересуется —
пожарные, экология, налоговая?»

**Примечания.** Распределение результатов в базе: 332 без выявленных нарушений,
7 с неизвестным результатом, 4 отменены. **Нарушений не выявлено ни в одной записи** —
то есть в текущем снапшоте этот блок скорее подтверждает благонадёжность,
чем сигнализирует о риске. Много проверок само по себе не негатив: у ЛЕ МОНЛИД
и СКВ СПБ по 100 записей, преимущественно предостережения.

#### `get_procurements(inn)`

**О чём.** Опыт госзакупок — редкий в этом наборе **позитивный** сигнал:

**Возвращает:** `tender_wins`, `contracts_signed`, `contracts_amount`,
разбивку `by_year[]` и `by_law[]` (44-ФЗ / 223-ФЗ / 94-ФЗ).

**Вопросы бизнеса:** «Есть ли у него опыт крупных контрактов и проходил ли он
чужую проверку?»

**Примечания.** Есть у 8 контрагентов. Показательные: ЮСКТ — 12 побед,
650,7 млн ₽ подписанных контрактов; СКВ СПБ — 101 победа, 64,8 млн ₽.
`contractSignedAmt` отсутствует в 1 записи из 16 — `null`, не ноль.

### 4.7. Сводные

#### `get_risk_factors(inn, chapter?)`

**О чём.** Зонтичный инструмент: все готовые формулировки банка одним запросом,
с фильтром по разделу или по выбранной роли анализа. Предметные инструменты
отдают свои факторы сами (§2.4), этот нужен для обзорных вопросов
и для роли «Общий».

**Возвращает:** `negative[]`, `positive[]` из `{code, chapter, name}`,
плюс `negative_total` и `negative_shown` — чтобы при фильтрации по роли было видно,
что показана часть.

Негативные факторы есть у 58 контрагентов: у 26 — один, у 17 — два, у 10 — три,
у 5 — четыре и более. Самые частые: `arbitrationDefendant` (32), `massOkved` (25),
`executionProceedings` (18), `massAddress` (13), `fnsBlocking` (9).

**Вопросы бизнеса:** «Что банк сам считает риском по этому контрагенту?»

**Примечание.** Коды в источнике записаны вперемешку кириллическими омоглифами
(`аrbitrationDefendant` с русской «а» в позитивных против латинского в негативных).
Нормализация на загрузке, наружу выходят только латинские коды.

#### `get_contractor_profile(inn)` / `get_contractor_full(inn)`

**О чём.** Готовый факт-пакет: `compact` для сравнения нескольких контрагентов,
`full` для карточки одного. Собирается `core/factpack.py`, включает результат
детектора расхождений и `get_legal_status` (§4.2).

Размеры замерены по всем 100 контрагентам: compact — медиана 840 токенов,
максимум 1030; full — медиана 2860, максимум 3740. Размер не зависит от того,
насколько велик исходный отчёт: тяжёлые массивы агрегируются кодом.

**Вопросы бизнеса:** «Дай общую картину» — типовой первый запрос.

## 5. Что осознанно не делается инструментом

| Идея | Почему нет |
|---|---|
| Список судебных дел | В источнике его нет — только агрегаты. Инструмент, который его обещает, спровоцирует галлюцинацию |
| `find_by_person` — поиск компаний по руководителю или учредителю | Проверено: внутри базы одна персона на двух контрагентах, ещё 3 ребра `relatedCompanies` с руководителем другого контрагента. Итого 2 компании из 100 — материала нет |
| `get_contacts` отдельным инструментом | Телефон, почта, сайт и адрес не тянут на отдельный вызов, живут в `get_basic_info` |
| Свои финансовые коэффициенты по балансу | Решение по проекту: нет `coefficient` — «нет данных». Считать самим запрещено |
| Свой порог для `massOkved` | Критерий не воспроизводится по данным (§3.3) |
| Численность персонала | `staff` пуст у всех 100 |
| Свёртка мелких инструментов в один вызов с параметром `section` | Разное покрытие и разные вопросы; отдельный инструмент модели дешевле, чем угадывание значения параметра |
| `resolve_contractor` — поиск контрагента по названию | Возвращает модели названия и ИНН реальных компаний на любой неточный запрос; состав базы утекает пользователю через ответ модели. Вместо него — переспрашивание (§4.1) |
| `search_contractors` — свободный поиск по базе по фильтрам (регион, вид деятельности, риск) | Тот же вектор утечки, что у `resolve_contractor`: инструмент возвращает модели названия и ИНН реальных компаний, и состав базы утекает пользователю через ответ модели. Ни «строки только по явному запросу», ни «только агрегаты без строк» приемлемого решения не дают. Из архитектуры исключён |
| Сплошная сверка всех чисел ответа с факт-пакетом | Ложные срабатывания на годах, порядковых числительных и округлениях сделали бы проверку дороже пользы. Оставлены три жёстких инварианта (§8.4) |

## 7. Инструменты по выборке

Работают не с одним контрагентом, а с несколькими. Все соглашения раздела 2
действуют без изменений; дополнительно каждый инструмент этой группы обязан
укладываться в бюджет контекста — compact-пакет стоит ~840 токенов медианно,
поэтому число контрагентов в ответе жёстко ограничено.

### 7.1. `compare_contractors(inns[], focus?)`

**О чём.** Сравнение 2–10 контрагентов, ИНН которых назвал пользователь.
Закрывает потребность, которую кейсодатель обозначил прямо: «Альфа-Банк не решает
задачу сравнения нескольких юрлиц — есть потребность сравнивать между собой разных
контрагентов и выбирать оптимального». Это же основа гипотезы про новый тариф.

| Параметр | Тип | Смысл |
|---|---|---|
| `inns` | str[] | 2–10 ИНН, все проходят проверку контрольного разряда |
| `focus` | enum? | `finance` / `legal` / `security` / `general` — какие колонки в сводке первыми |

**Возвращает:**

| Поле | Смысл |
|---|---|
| `items[]` | compact-пакеты по каждому контрагенту |
| `matrix` | сводная таблица: строка — контрагент, колонка — показатель |
| `differences[]` | **различия, посчитанные кодом**: у кого хуже светофор, выше долговая нагрузка, отсутствует отчётность, больше негативных факторов |
| `ranking` | порядок по названному критерию, посчитанный кодом |
| `not_found[]` | ИНН, которых нет в базе — отдельно, вызов из-за них не падает |

Колонки `matrix`: оба светофора, `severity` правового статуса, возраст, размер,
выручка и прибыль последнего года, чистые активы, `debt_to_net_assets`,
активные исполнительные производства, открытый арбитраж как ответчик,
число негативных факторов, число расхождений детектора.

**Вопросы бизнеса:** «Выбираю между тремя поставщиками — кто надёжнее и в чём именно
разница», «у кого из них хуже всего с деньгами».

**Примечания.**
* Ранжирование считает **код**, не модель: критерий передаётся именем
  (`risk`, `debt_burden`, `revenue`, `age`), а не формулируется моделью на ходу.
* Контрагенты с отсутствующей отчётностью не проваливаются в конец рейтинга —
  они получают `comparable: false` и выносятся отдельной группой. Отсутствие данных
  не равно плохому показателю (прямое указание кейсодателя: пропуски в данных —
  это отсутствие информации, а не проблема контрагента).
* Вердикт по каждому строится на его собственном `risk_level`; сводного вердикта
  «работайте с этим» инструмент не выдаёт — решение остаётся за пользователем.

---

### 7.2. `find_similar_contractors(inn, limit=5)`

**О чём.** Контрагенты, похожие на заданного: тот же раздел ОКВЭД и тот же регион.
Вход в сценарий «дай альтернативу» и в рекомендацию Альфа-таргета.

| Параметр | Тип | Смысл |
|---|---|---|
| `inn` | str | опорный контрагент, уже названный пользователем |
| `limit` | int = 5 | потолок выдачи |

**Возвращает:** `match_level`, `total`, `items[]` из
`{inn, short_name, region, main_okved, risk_level, zsk_risk_level}`
плюс `basis` — по каким признакам искали.

`match_level` обязателен и принимает два значения:

| Значение | Когда | Что означает для модели |
|---|---|---|
| `region_and_activity` | нашлись в том же регионе и разделе ОКВЭД | точное совпадение |
| `activity_only` | в регионе никого, деградировали до раздела | **другой регион**, модель обязана это проговорить |

**Проверено на данных.** Строгое совпадение «регион + раздел ОКВЭД» покрывает
лишь **24 контрагента из 100**, поэтому деградация до одного раздела обязательна —
она поднимает охват до 89. Пар с двумя и более контрагентами: по региону
и разделу — 6, крупнейшая «Москва + оптовая торговля» — 13 компаний.
Разделы ОКВЭД в базе: `46` — 28 контрагентов, `41` — 16, `43` — 11, `49` и `68` — по 6.

**Вопросы бизнеса:** «С кем ещё можно работать вместо него», «кто в моём регионе
делает то же самое».

**Примечания.**
* Сходство считается **только по разделу ОКВЭД и региону**. Похожесть по выручке,
  размеру или риску не считаем: это уже подбор «получше», то есть скрытая
  рекомендация, а её агент давать не должен.
* Предприниматели в выдачу по региону не попадают — адреса нет ни у одного из 25 (§3.1).
  Наружу это не выходит (§2.5), инструмент просто деградирует до `activity_only`.
* ИНН из ответа попадают в белый список сессии (§4.1) — переход к найденному
  контрагенту легален.

## 8. Продвинутые инструменты

### 8.1. `run_focused_analysis(inn, focus)`

**О чём.** Суб-агент под узкий разбор. Ходит собственным циклом по инструментам
своей группы и возвращает основному агенту готовый структурированный вывод,
а не десяток сырых ответов.

| `focus` | Инструменты, доступные суб-агенту |
|---|---|
| `finance` | `get_financials`, `get_balance_sheet`, `get_liabilities`, `get_financial_ratios`, `get_debt_burden` |
| `legal` | `get_arbitration`, `get_execution_proceedings`, `get_legal_status`, `get_debt_burden` |
| `security` | `get_fns_flags`, `get_ownership`, `get_affiliations`, `get_legal_status` |
| `activity` | `get_activity`, `get_licenses`, `get_inspections`, `get_procurements` |

**Возвращает:** `findings[]` из `{statement, source_fields[], severity}`,
`summary` на 1–2 строки, `missing[]` — чего не хватило для вывода.
`source_fields` обязательно: без ссылки на поле утверждение не принимается.

**Зачем.** Глубина без раздувания контекста: основной агент получает вывод
на ~300 токенов вместо пяти ответов инструментов на ~2000. Заодно закрывает
гипотезу про кнопки предзаданных видов анализа в интерфейсе — кнопка роли
дёргает соответствующий `focus`.

**Примечания.**
* Суб-агент **не имеет доступа к сырым данным** — только к тем же инструментам,
  что и основной агент. Правила раздела 2 действуют внутри него без исключений.
* Суб-агент не формулирует вердикт и не даёт рекомендаций — только тезисы
  со ссылками. Вердикт собирает основной агент из `risk_level`.
* Латентность растёт: каждый вызов — отдельный цикл к LLM. Кейсодатель сказал,
  что для агентского решения латентность не критична, но **обязательно
  сигнализировать пользователю о ходе работы** — статус «идёт финансовый анализ»
  должен доходить до интерфейса.

### 8.2. `build_chart(target, chart_type)`

**О чём.** Возвращает **данные для графика, а не картинку**. Рисует фронт
компонентами Альфы; модель не имеет права выводить числа таблицей в тексте
там, где уместен график.

| Параметр | Тип | Смысл |
|---|---|---|
| `target` | str \| str[] | ИНН или список ИНН для сравнительных графиков |
| `chart_type` | enum | см. таблицу ниже |

**Возвращает:** `{type, series[], labels[], unit, source_fields[], missing_points[]}`.

| `chart_type` | Что показывает | Данные | Покрытие |
|---|---|---|---|
| `revenue_profit` | выручка и прибыль по годам | `fin_reports` 2023–2025 | 67 контрагентов |
| `execproc_timeline` | возбуждённые производства по годам | `execution_proceedings.date` | 53 |
| `arbitration_sides` | истец против ответчика по годам | `arbitration_by_year` | 44 |
| `balance_structure` | активы против обязательств и капитала | `fin_reports` | 67 |
| `debt_vs_assets` | текущий долг на фоне чистых активов | `get_debt_burden` | 67 |
| `compare_metric` | один показатель у нескольких контрагентов | compact-пакеты | — |

**Зачем.** Три причины, и ни одна не косметическая: числа в графике берутся
из того же факт-пакета, что проверяет валидатор; график снимает когнитивную
нагрузку, которая и есть исходная боль клиента; `source_fields` позволяет
проверить график тем же способом, что и текст.

**Примечания.**
* `missing_points[]` обязателен: пропуск в ряду отдаётся как разрыв,
  а не как ноль. Прибыль раскрыта лишь в 41 % отчётов — молчаливая замена
  на ноль превратит отсутствие данных в убыток.
* Инструмент не выбирает тип графика сам и не решает, нужен ли график.

### 8.3. `draft_followup_questions(inn)`

**О чём.** Список того, что имеет смысл запросить у контрагента, собранный
**детерминированно из `missing_data` и негативных факторов**.

| Триггер | Что предлагается запросить |
|---|---|
| нет финансовой отчётности | бухгалтерский баланс и отчёт о финансовых результатах за последний год |
| активные исполнительные производства | справку об отсутствии задолженности, пояснение по действующим взысканиям |
| `invalidAddress` / `massAddress` | подтверждение фактического места нахождения, договор аренды |
| `fnsBlocking` | пояснение по блокировке счёта и срок её снятия |
| `severity: critical` в правовом статусе | выписку из ЕГРЮЛ на текущую дату |
| открытый арбитраж как ответчик | пояснение по предмету и стадии спора |
| отрицательные чистые активы | пояснение по источникам покрытия обязательств |
| отмечены коды ОКВЭД из «серого» перечня (`massOkved`) | уточнение профильного вида деятельности по предмету договора |
| метка о номинальном руководителе или недостоверных данных о нём | документы, подтверждающие полномочия руководителя |

**Возвращает:** `items[]` из `{question, reason, source_field}` — вопрос,
чем он вызван и на каком поле основан.

**Зачем.** Кейсодатель запретил решения: «агент должен быть максимально сухим,
только подсвечивать риски и делать аккуратные рекомендации, мы не должны нести
ответственность за принятые решения клиента». Список вопросов — самая безопасная
форма пользы: он не говорит «работайте» или «не работайте», а даёт следующее
действие. И это прямой драйвер возврата в сервис, то есть работает на ключевую
метрику кейсодателя — retention.

**Примечания.** Формулировки — из фиксированного шаблонного набора, привязанного
к коду триггера. Модель их не сочиняет и не расширяет: инструмент детерминирован
целиком, LLM здесь не участвует.

Триггер «нет лицензии при лицензируемом виде деятельности» не реализуем:
справочника лицензируемых ОКВЭД в источнике нет, а угадывать его — значит
обвинить контрагента в работе без лицензии на пустом месте (§4.5).

### 8.4. `validate_answer(answer, context)`

**О чём.** Детерминированная проверка ответа модели перед отдачей пользователю.
Вызывается **кодом в узле графа**, модели не отдаётся.

Проверяются три инварианта, и только они:

| # | Проверка | Что ловит |
|---|---|---|
| 1 | все ИНН в ответе принадлежат белому списку сессии | выдуманный ИНН — пользователь проверит не ту компанию |
| 2 | вердикт не мягче, чем `risk_level` факт-пакета | ответ оптимистичнее оценки самого банка |
| 3 | при непустых `discrepancies` они упомянуты в тексте | умолчание о расхождении светофора и фактов |

Проверка вердикта **односторонняя**: ответ строже светофора допустим и прямо
ожидается при сработавшем детекторе расхождений — в этом и состоит ценность
продукта поверх исходного отчёта. Нарушением считается только обратное:
«работать» при `HIGH`, «работать» при `MEDIUM`. Строгость шкалы:
Работать → Работать с осторожностью → Не рекомендуется.

Провал → один повтор с указанием конкретной ошибки → при повторном провале
отдаётся детерминированный отчёт (`architecture.md` §14).

**Почему объём проверки сужен.** Изначально в `architecture.md` §11 заложена
сплошная сверка **всех** чисел ответа с факт-пакетом. От неё отказались:
в развёрнутом ответе десятки чисел — годы, порядковые числительные, доли,
округления вида «254,5 млн» против `254507229`. Ложные срабатывания сделали бы
каждый второй ответ поводом для повтора, а это латентность и токены на пустом месте.

Три оставшихся инварианта однозначны, не дают ложных срабатываний и ловят именно
те ошибки, которые дорого стоят. Проверка чисел по смыслу переходит
к `validate_conclusions` (§8.5).

**Расхождение с `architecture.md` §11 зафиксировано и требует правки того документа.**

---

### 8.5. `validate_conclusions(answer, fact_pack)`

**О чём.** Второй проход LLM: проверка **семантики**, а не арифметики.
Отвечает на вопрос «следует ли этот вывод из этих фактов».

**Возвращает:** `{passed, issues[]}`, где `issue` — `{claim, problem, source_field}`.

Типы нарушений, на которые настраивается проверка:

| Тип | Пример |
|---|---|
| вывод не следует из фактов | «компания финансово стабильна» при отрицательных чистых активах |
| отсутствие данных подано как факт | «у компании нет долгов» вместо «данных о долгах в отчёте нет» |
| скрытая рекомендация | «можно смело работать» — прямой запрет кейсодателя |
| раскрытие полноты базы | «известно только по N компаниям» (§2.5) |
| описание конкретного судебного дела | в источнике только агрегаты (§3.2) |

**Статус.** Интерфейс объявляется, реализация — за флагом конфига.
Включается после того, как основной контур заработает: это второй вызов LLM
на каждый ответ, то есть удвоение стоимости и латентности.

**Примечание.** Валидатор получает факт-пакет и ответ — и ничего больше.
Доступа к сырым данным и к инструментам у него нет, иначе он начнёт
достраивать факты вместо проверки.

## 9. Спецификация инструментов

Раздел предназначен для реализации: по каждому инструменту дан текст, который уйдёт
в FastMCP как `description`, и таблицы входа и выхода. Текст `description` модель видит
дословно — он написан для неё, а не для разработчика, и в нём умышленно проговорены
границы данных и запреты.

### 9.0. Что вынесено в системный промпт и не дублируется в каждом описании

Чтобы описания не разбухали, общие соглашения задаются один раз в системном промпте:

* каждый ответ содержит `found`, `inn`, `as_of` — дату отчёта; данные не «сегодняшние»;
* `null` — данных нет в источнике, это **не ноль**;
* `"not_applicable"` — поле неприменимо к этому типу лица;
* `missing[]` — перечень полей, по которым данных нет;
* база закрыта: ИНН вне её — ошибка, а не пустой ответ;
* полнота базы наружу не раскрывается (§2.5).

В `description` каждого инструмента остаётся только то, что специфично для него.

Не все перечисленные здесь инструменты попадают в промпт одновременно — состав
набора на конкретном шаге описан в §10. Инструмент `load_tools`, управляющий
подгрузкой, специфицирован там же (§10.6).

`obj`, `[]` — массив. Все суммы — целые рубли числом.

### `get_legal_status(inn) -> dict`

> Правоспособность контрагента по ЕГРЮЛ: действует ли юридическое лицо и не начата ли
> процедура его прекращения. Ключевое: поле `status` почти всегда равно `CURRENT`
> и само по себе ничего не означает — смотри на `status_reason` и `severity`.
> Значение `severity = "critical"` означает банкротство или предстоящее исключение
> из реестра; такой факт обязательно проговаривается в ответе, **даже если светофор
> зелёный**. Значение `attention` — маркер грядущих изменений, о нём стоит упомянуть
> как о поводе уточнить.

**Вход:** `inn: str`.

| Выход | Тип | Смысл и значения |
|---|---|---|
| `status` | enum | `CURRENT` \| `CLOSED` |
| `status_date` | date \| null | дата присвоения статуса |
| `status_reason` | str \| null | текст причины из ЕГРЮЛ |
| `severity` | enum | `critical` — банкротство или предстоящее исключение из ЕГРЮЛ; `attention` — смена места нахождения, уменьшение уставного капитала; `none` — причины нет |
| `factors[]` | obj[] | метки банкротства и ликвидации (`liquidationStatus`) |

**Реализация.** Подмешивается в факт-пакет всегда, не по решению модели (§4.2).

### `get_financials(inn, year_from=None, year_to=None) -> dict`

> Отчёт о финансовых результатах: выручка и прибыль по годам плюс тренд, посчитанный
> кодом. Прибыль может быть отрицательной — это убыток. Пустое значение прибыли
> означает, что показатель не раскрыт: это **не ноль и не убыток**, и так примерно
> в половине отчётов. Если `available = false`, финансовой отчётности нет вовсе —
> не интерпретируй это как отсутствие деятельности или как плохой показатель.
> Тренд уже посчитан, выводить его самостоятельно из чисел не нужно.

**Вход:** `inn: str`, `year_from: int = None`, `year_to: int = None` — границы периода;
в источнике доступны 2023–2025.

| Выход | Тип | Смысл и значения |
|---|---|---|
| `available` | bool | есть ли отчётность |
| `years[]` | obj[] | `{year, proceeds, profit}` |
| `proceeds` | int \| null | выручка, ₽ |
| `profit` | int \| null | прибыль или убыток, ₽; отрицательное значение — убыток |
| `trend` | obj | `{proceeds, profit}`, каждое: `growing` \| `flat` \| `declining` \| null |
| `factors[]` | obj[] | факторы раздела `finance` |

### `get_balance_sheet(inn, year=None) -> dict`

> Активы и собственный капитал по годам: валюта баланса, оборотные и внеоборотные
> активы, запасы, дебиторская задолженность, денежные средства, основные средства,

| Выход | Тип | Смысл |

| `years[]` | obj[] | по каждому году поля ниже |
| `total_assets` | int \| null | валюта баланса, ₽ |
| `net_assets` | int \| null | чистые активы (собственный капитал), ₽; может быть отрицательным |
| `current_assets`, `uncurrent_assets` | int \| null | оборотные и внеоборотные активы |
| `stocks`, `receivables`, `bankroll`, `fixed_assets` | int \| null | запасы, дебиторская задолженность, денежные средства, основные средства |
| `negative_net_assets` | bool | чистые активы отрицательны в последнем году |

### `get_financial_ratios(inn) -> dict`

> Готовые финансовые коэффициенты из отчёта: устойчивость, платёжеспособность,
> рентабельность. Значения приходят из источника и самостоятельно не рассчитываются.
> Если блока нет — данных нет, и выводить коэффициенты из баланса запрещено.
> Точные формулы расчёта банк не раскрыл, поэтому называй значение и его смысл,

| `sustainability` | float \| null | финансовая устойчивость — доля устойчивых источников в активах; отрицательное значение означает, что капитал проеден |
| `solvency` | float \| null | платёжеспособность — покрытие обязательств имеющимися средствами; ориентир — около единицы |
| `profitability` | float \| null | рентабельность, %; отрицательное значение — убыточная деятельность |

### `get_debt_burden(inn) -> dict`

> Соотносит текущую долговую нагрузку с масштабом бизнеса и отвечает на вопрос,
> критичны эти долги или находятся в пределах погрешности. Текущий долг — это
> действующие исполнительные производства плюс открытый арбитраж, где контрагент
> выступает ответчиком; завершённые дела в него не входят. Сравнение идёт с чистыми
> активами и выручкой. Если `comparable = false`, соотносить не с чем: приводи
> абсолютные суммы и **не оценивай их критичность**. Одна и та же сумма для
> микропредприятия катастрофична, а для крупной компании находится в пределах
> погрешности — поэтому абсолютные пороги здесь неприменимы.

**Вход:** `inn: str`.

| Выход | Тип | Смысл |
|---|---|---|
| `current_debt` | int | текущий долг, ₽ |
| `debt_parts` | obj | `{execproc_active, arbitration_pending_defendant}` — из чего сложился |
| `net_assets`, `revenue` | int \| null | база сравнения, последний год |
| `debt_to_net_assets` | float \| null | доля долга от чистых активов; пусто, если капитал отрицателен или отчётности нет |
| `debt_to_revenue` | float \| null | доля долга от выручки |
| `basis` | enum | `net_assets` \| `revenue` \| `absolute` — на чём построена оценка |
| `comparable` | bool | есть ли с чем соотносить |

### `get_arbitration(inn, year_from=None, year_to=None) -> dict`

> Арбитражные споры в агрегированном виде. **Конкретных дел в источнике нет**:
> ни номеров, ни сторон, ни предметов спора — описывать отдельные дела запрещено.
> Роль контрагента меняет смысл радикально: истец взыскивает свои деньги, ответчик
> рискует не рассчитаться. Поля `pending` — открытые дела, то есть текущий риск;
> остальное завершено. Общее число дел бери только из `total_count`: сумма дел истца
> и ответчика меньше общего числа, часть дел не классифицирована по стороне,
> **складывать стороны нельзя**.

**Вход:** `inn: str`, `year_from: int = None`, `year_to: int = None`; в источнике 2023–2026.

| Выход | Тип | Смысл |
|---|---|---|
| `granularity` | enum | всегда `aggregates_only` |
| `total_count`, `total_amount` | int \| null | всего дел и сумма требований |
| `as_plaintiff` | obj | `{count, amount, pending_count, pending_amount}` — контрагент истец |
| `as_defendant` | obj | то же — контрагент ответчик |
| `by_year[]` | obj[] | `{year, plaintiff_count, plaintiff_amount, defendant_count, defendant_amount}` |
| `factors[]` | obj[] | факторы раздела `arbitr` |

### `get_execution_proceedings(inn, active_only=True, limit=5) -> dict`

> Исполнительные производства — стадия принудительного взыскания после суда,
> более тревожный сигнал, чем сам спор. Возвращает две пары счётчиков: действующие
> взыскания и всего за историю, включая закрытые. Разница между ними может быть
> на два порядка, поэтому **всегда уточняй, о каких именно идёт речь**: закрытое
> производство 2014 года не является текущей проблемой. Полный список не отдаётся —
> только агрегат, крупнейшие действующие и распределение по годам возбуждения.

**Вход:** `inn: str`, `active_only: bool = True` — включать ли закрытые в `top`,
`limit: int = 5` — сколько крупнейших вернуть.

| Выход | Тип | Смысл |
|---|---|---|
| `active`, `active_amount` | int | **действующие** производства и их сумма, ₽ |
| `total`, `total_amount` | int | за всю историю, включая закрытые |
| `top[]` | obj[] | `{number, date, amount}`, до `limit` крупнейших |
| `top_scope` | enum | `active` \| `all` — что попало в `top`; при `active_only=false` туда входят и закрытые |
| `by_year` | obj | `{год: количество}` по дате возбуждения |
| `factors[]` | obj[] | факторы раздела `execproc` |

### `get_affiliations(inn) -> dict`

> Связанные компании контрагента: наименования, ИНН, руководители. Поле
> `same_director_count` показывает, сколько из них возглавляет тот же человек —
> это признак группы компаний, а не случайных связей. `in_database` перечисляет
> те связанные компании, которые есть в базе и которые можно проверить остальными
> инструментами; обычно этот список пуст. Наличие связей само по себе нейтрально
> и рисков не означает.

**Вход:** `inn: str`, `limit: int = 20`.

| Выход | Тип | Смысл |
|---|---|---|
| `count` | int | всего связанных компаний |
| `same_director_count` | int | из них под тем же руководителем |
| `in_database[]` | str[] | ИНН связанных, доступных для проверки |

### `get_risk_factors(inn, chapter=None) -> dict`

## 9.2. Инструменты по выборке

### `compare_contractors(inns, focus=None) -> dict`

> Сравнение от двух до десяти контрагентов по ИНН, названным пользователем.
> Возвращает сводную таблицу, различия и ранжирование, посчитанные кодом —
> считать и ранжировать самостоятельно не нужно. Контрагенты без финансовой
> отчётности выносятся отдельной группой: **отсутствие данных не означает плохой
> показатель** и не должно опускать их в рейтинге. Сводного вывода «работайте
> с этим» инструмент не даёт, и давать его не следует — решение принимает
> пользователь, инструмент лишь показывает различия.

**Вход:** `inns: str[]` — от 2 до 10; `focus: enum = None` — `finance` \| `legal`
\| `security` \| `general`, определяет порядок колонок; `rank_by: enum = None` —
`risk` \| `debt_burden` \| `revenue` \| `age`.

| Выход | Тип | Смысл |
|---|---|---|
| `items[]` | obj[] | сокращённые пакеты по каждому |
| `matrix` | obj | сводная таблица: строка — контрагент, колонка — показатель |
| `differences[]` | obj[] | `{metric, text}` — чем контрагенты отличаются |
| `ranking[]` | obj[] | порядок по `rank_by`, посчитанный кодом |
| `not_comparable[]` | str[] | ИНН, по которым выбранный критерий не считается; в рейтинг не попадают, но и в конец не опускаются |
| `not_found[]` | str[] | ИНН, которых нет в базе; вызов из-за них не падает. Если не найден ни один — ответ `found: false` |

`focus` определяет **порядок колонок** в `matrix`: модель читает объект сверху вниз,
поэтому первым идёт то, ради чего сравнение затеяли. Состав колонок при этом
не меняется. Значение `activity` фильтр факторов в пакетах не включает —
такой роли в `core/roles.py` нет.

Колонки `matrix`: оба светофора, `severity` правового статуса, возраст, размер,
выручка и прибыль последнего года, чистые активы, `debt_to_net_assets`,
действующие исполнительные производства, открытый арбитраж как ответчик,
число негативных факторов, число расхождений.

### `find_similar_contractors(inn, limit=5) -> dict`

> Контрагенты, похожие на заданного по виду деятельности и региону. Поле
> `match_level` обязательно к прочтению: `region_and_activity` — совпали и регион,
> и вид деятельности; `activity_only` — **регион не совпал**, и это нужно прямо
> сказать пользователю. Сходство считается только по разделу ОКВЭД и географии:
> инструмент не подбирает «более надёжного» и его выдача не является рекомендацией.

**Вход:** `inn: str` — опорный контрагент; `limit: int = 5`.

| Выход | Тип | Смысл и значения |
|---|---|---|
| `match_level` | enum | `region_and_activity` — совпали регион и раздел ОКВЭД; `activity_only` — только раздел; `none` — не нашлось. **Если региона у контрагента нет вовсе, уровень сразу `activity_only`**: выдавать совпадение за географическое нельзя |
| `basis` | obj | `{region, okved_division}` — по каким признакам искали |
| `total` | int | найдено всего |
| `items[]` | obj[] | `{inn, short_name, region, main_okved, risk_level, zsk_risk_level}` |

### `validate_answer(answer, context) -> dict`

**Служебный. Вызывается кодом в узле графа перед отправкой ответа, модели
не предоставляется.** Описание для разработчика, не для промпта.

Проверяет три инварианта: все ИНН из ответа принадлежат белому списку сессии;
вердикт согласован с `risk_level`; при непустых `discrepancies` они упомянуты
в тексте. Сплошная сверка чисел сознательно не выполняется (§8.4).

**Вход:** `answer: str`, `context: dict` — факт-пакет и белый список ИНН сессии.

| Выход | Тип | Смысл |
|---|---|---|
| `passed` | bool | все инварианты соблюдены |
| `violations[]` | obj[] | `{rule, detail}`; `rule`: `unknown_inn` \| `verdict_mismatch` \| `discrepancy_omitted` |

При провале — один повтор с указанием ошибки, затем детерминированный отчёт.

## 10. Какой набор инструментов видит модель

Раздел 9 описывает инструменты по отдельности. Этот описывает, **какие из них
попадают в промпт на конкретном шаге и почему не все сразу**.

### 10.1. Проблема

Замер токенизатором `o200k_base` — то же семейство, что у GPT-OSS:

| Что | Значение |
|---|---|
| Инструментов, видимых модели | 24 |
| Все описания и схемы входа | **3 439 токенов** |
| Медиана на инструмент | 105 токенов |
| Контекст GPT-OSS-120B | 131 072 токена |

**По токенам проблемы нет.** Механизм Tool Search в Claude Code включается,
когда описания превышают 10 тыс. токенов, — мы втрое ниже порога, и 3,4 тыс.
это 2,6 % окна. Известные жалобы на «55 тыс. токенов до первого сообщения»
относятся к сборкам из десяти MCP-серверов по 20–80 инструментов каждый.

**Проблема в другом — в числе одновременных вариантов выбора.** Практика
и замеры сходятся: надёжная зона — 10–20 инструментов в активной ротации;
выше 15–20 точность выбора заметно падает; успешность держится выше 90 %
примерно до 30 кандидатов, а дальше обрывается нелинейно. У нас 24, и работать
будет открытая 120B-модель, у которой выбор слабее, чем у моделей из этих замеров.

Отсюда цель: **сократить не объём описаний, а число инструментов, между которыми
модель выбирает за один шаг.**

### 10.2. Принцип: набор собираем мы, а не ищет модель

Tool Search — функция *клиента*: он видит раздутый список и подсовывает модели
поисковик по инструментам. Но клиентом здесь являемся мы: агент сам формирует
запрос к LLM и полностью контролирует поле `tools`. Мы знаем активную роль
и текст запроса — значит, можем сразу отдать нужное подмножество.

Серверная сборка списка надёжнее и дешевле обнаружения на стороне модели:
без лишнего круга и без риска, что модель не догадается воспользоваться поиском.

### 10.3. Три слоя

| Слой | Что | Кто решает |
|---|---|---|
| 1. Ядро | 9 инструментов, доступны всегда | фиксировано |
| 2. Ролевой набор | добавляется по нажатой кнопке роли **и** роутером по ключевым словам запроса | код |
| 3. `load_tools` | аварийный выход, когда роутер промахнулся | модель |

Слои 1 и 2 закрывают подавляющее большинство случаев без единого лишнего вызова.
Слой 3 существует ради одного сценария — см. §10.6.

### 10.4. Состав наборов

**Ядро (9).** Работают в любом сценарии и не привязаны к предметной области:

`get_contractor_full`, `get_legal_status`, `get_basic_info`, `get_risk_factors`,
`compare_contractors`, `run_focused_analysis`, `build_chart`,
`draft_followup_questions`, `load_tools`.

`get_legal_status` в ядре потому, что правоспособность проверяется всегда (§4.2).
`get_contractor_full` — потому, что его сводка перекрывает большинство вопросов
не по своей роли и служит подстраховкой второго уровня.

**Предметные наборы:**

| Область | Инструменты | Токенов |
|---|---|---:|
| `finance` | `get_financials`, `get_balance_sheet`, `get_liabilities`, `get_financial_ratios`, `get_debt_burden` | 742 |
| `legal` | `get_arbitration`, `get_execution_proceedings`, `get_debt_burden` | 520 |
| `security` | `get_fns_flags`, `get_ownership`, `get_affiliations`, `find_similar_contractors` | 552 |
| `activity` | `get_activity`, `get_licenses`, `get_inspections`, `get_procurements` | 442 |

`get_debt_burden` входит в два набора намеренно: он отвечает и на финансовый
вопрос о масштабе долга, и на юридический о тяжести взысканий.

**Итоговый размер промпта по ролям:**

| Роль | Инструментов | Токенов |
|---|---:|---:|
| Ядро без роли | 9 | 1 368 |
| Финансовый | 14 | 2 110 |
| Юридический | 12 | 1 888 |
| Безопасность | 13 | 1 920 |
| Деятельность | 13 | 1 810 |
| Общий | 24 | 3 439 |

Экономия — **38 % токенов**, но важнее другое: 24 инструмента превращаются
в 12–14, то есть набор садится в середину надёжной зоны вместо её края.
Роль «Общий» по-прежнему отдаёт всё — это рабочий режим, просто не режим
по умолчанию.

**Не выдаются модели вовсе:** `get_contractor_profile` — используется
`compare_contractors` внутри (два похожих инструмента «полный» и «сокращённый»
в одном списке провоцируют ошибку выбора); `validate_answer`
и `validate_conclusions` — вызываются кодом в узлах графа.

### 10.5. Роутер: добавление набора по теме запроса

Узел `router` (`architecture.md` §10) уже разбирает входящее сообщение.
Он же добавляет предметный набор к ролевому по ключевым словам:

| Слова в запросе | Набор |
|---|---|
| выручка, прибыль, убыток, доход, баланс, активы, капитал, долг, задолженность, обязательства, рентабельность, кредит | `finance` |
| суд, судится, арбитраж, иск, ответчик, истец, пристав, взыскание, исполнительное производство | `legal` |
| директор, руководитель, учредитель, владелец, налоговая, ФНС, блокировка, счета, адрес, реестр, связанные, аффилированные | `security` |
| ОКВЭД, деятельность, лицензия, разрешение, проверка, надзор, тендер, закупка, госконтракт | `activity` |

Сопоставление детерминированное, стоит миллисекунды, лишнего круга не требует
и от решения модели не зависит. Наборы складываются: запрос про суды и выручку
подтянет оба.

### 10.6. `load_tools(area)` — аварийный выход

**Какую проблему решает.** Роутер работает по ключевым словам и неизбежно
промахивается на непрямых формулировках: «сколько он зарабатывает» вместо
«выручка», «чем он рискует» вместо «арбитраж». В этот момент модель видит
ролевой набор, нужного инструмента в нём нет — и отвечает «таких данных нет»,
хотя данные есть.

Это зеркальная ошибка к галлюцинации и не менее вредная: весь документ выстроен
вокруг того, чтобы агент не выдумывал, но отказ при наличии данных бьёт
по критерию «отвечает на большинство вопросов при тестировании» ровно так же.

**Как работает.** Модель вызывает инструмент, бэкенд добавляет весь набор
области к уже отданным, и следующим шагом **того же агентного цикла** модель
видит расширенный список. Список аддитивный, накопленное не сбрасывается.
Пользователь отдельного сообщения не пишет и лишнего ожидания не видит.

```
шаг 1  tools = [ядро(9), security(4)]
       модель: load_tools(area="finance")
       бэкенд: {"loaded": ["get_financials", "get_balance_sheet",
                           "get_liabilities", "get_financial_ratios",
                           "get_debt_burden"]}
шаг 2  tools = [ядро(9), security(4), finance(5)]
       модель: get_financials(inn="...")
```

**Ключевое: это указатель, а не каталог.** Полные описания подгруженных
инструментов приезжают сами, в поле `tools` следующего запроса. Дублировать их
в описании `load_tools` не нужно — достаточно, чтобы модель поняла, в какой
области искать. Поэтому в описании перечисляются **темы**, а не инструменты,
а вызов возвращает только имена — как подтверждение.

Замеры вариантов описания:

| Вариант | Токенов |
|---|---:|
| Короткие подсказки по темам (принято) | **163** |
| Состав наборов расписан по инструментам | 386 |
| Четыре отдельных `describe_<area>` | ~304 |

Развёрнутый вариант стоит 12 % от полного списка инструментов, и при этом
модели всё равно нужен лишний круг — платим и за каталог, и за задержку,
получая то же самое.

#### Описание для FastMCP

> Подгружает дополнительный набор инструментов, если нужного среди доступных нет.
> Вызывай только тогда, когда для ответа не хватает данных, а подходящего
> инструмента в списке не видно. Подгруженные инструменты становятся доступны
> сразу — следующим шагом вызывай нужный.
>
> area:
>   finance — выручка, прибыль, убыток, баланс, активы, обязательства,
>             долговая нагрузка, коэффициенты
>   legal — арбитражные споры, исполнительные производства, взыскания
>   security — метки налоговой, блокировка счетов, учредители, руководитель,
>              связанные компании
>   activity — виды деятельности ОКВЭД, лицензии, проверки надзорных органов,
>              госзакупки

**Вход:** `area: enum` — `finance` \| `legal` \| `security` \| `activity`.

| Выход | Тип | Смысл |
|---|---|---|
| `loaded[]` | str[] | имена ставших доступными инструментов |

**Отличие от `run_focused_analysis`.** Оба ведут «в область», и их легко спутать.
`run_focused_analysis` **делегирует разбор** и возвращает готовые тезисы —
годится, когда нужен вывод. `load_tools` **даёт доступ к сырым инструментам** —
нужен, когда требуется конкретное число, которого в тезисах не будет.
Различие проговорено в описаниях обоих.

### 10.7. Что осознанно не делается

| Идея | Почему нет |
|---|---|
| Четыре инструмента `describe_<area>` вместо одного `load_tools` | Дороже (~304 против 163 токенов) и заставляет модель выбирать между четырьмя почти одинаковыми описаниями — а именно на близких по смыслу инструментах она и путается. Механизм подгрузки нужен в обоих вариантах: инструмент, который только возвращает описания, бесполезен — вызвать инструмент, отсутствующий в поле `tools`, модель всё равно не может |
| Tool Search / `defer_loading` | Порог включения — 10 тыс. токенов описаний, мы втрое ниже. Добавляет круг и режим отказа, когда модель не вызывает поиск |
| Иерархия и пространства имён в духе SEP-993 | Предложение в спецификации MCP не принято, на нашем масштабе выигрыш нулевой |
| Сокращение самих описаний | Медиана 105 токенов, и бо́льшая их часть — границы данных и запреты («стороны арбитража не складывать», «ноль лицензий не равно нарушению»). Резать можно что угодно, кроме этого: именно эти строки удерживают модель от выдумывания |
| Сжатие ответов инструментов | Ответы уже агрегаты, а не сырые массивы. Вернуться, если появятся объёмные выдачи |
